## Day 43 —— 搭建复现环境：独立环境与踩坑手册

> **一句话**：复现的第一步不是跑代码，是**造一个不会污染其他项目的独立环境**，并把每个报错抄下来 —— 这份踩坑手册，就是你论文"实验设置"章节的原材料。

### 一、为什么必须建独立环境

新手最常见的做法是直接在 base 环境里 `pip install -r requirements.txt`。后果是：**你三个月前的另一个项目突然跑不起来了**，而且你根本不知道是谁弄坏的。

依赖冲突在深度学习里是常态，原因很具体：

| 冲突来源 | 典型表现 |
|---|---|
| **numpy 大版本跃迁** | numpy 2.x 删掉了一批老 API，2023 年前的代码直接 `AttributeError` |
| **torch / torchvision 强绑定** | 版本不配套时，`import torchvision` 报 `operator torchvision::nms does not exist` |
| **CUDA 编译扩展** | 需要本机 `nvcc`，缺了就只能装 CPU 版，训练慢十倍 |
| **底层编译依赖缺失** | 缺 `gcc` / `ninja`，装到一半卡在 building wheel |

```bash
# 一个项目一个环境，命名带项目特征，不要叫 test1 / test2
conda create -n repro-fdia python=3.10 -y
conda activate repro-fdia

# 立刻验证三件事：Python 版本、torch 版本、CUDA 是否可用
python -c "import sys, torch; print(sys.version); print(torch.__version__, torch.cuda.is_available())"
```

> **`torch.cuda.is_available()` 返回 False 就别往下走了。** 先解决这个，否则后面所有"训练太慢"的抱怨都是白费时间。

### 二、按 README 装依赖的正确优先级

README 里往往给了好几种装法，按这个顺序挑，**能往上就不往下**：

| 优先级 | 文件 / 方式 | 说明 |
|---|---|---|
| 1 | `requirements.txt` | 最标准，`pip install -r requirements.txt` |
| 2 | `environment.yml` | conda 导出的完整环境，含 CUDA 工具链 |
| 3 | `pyproject.toml` / `setup.py` | 通常是 `pip install -e .`，说明这是个可安装包 |
| 4 | README 里的散装命令 | 最容易漏装，装完记得 `pip freeze` 存一份 |
| 5 | `Dockerfile` | 最靠谱，直接 `docker build`，环境差异归零 |

**CUDA 与 PyTorch 版本匹配**：不要凭记忆写版本号，去 PyTorch 官网的 Previous Versions 页面查对应表 —— 这张表每年都在变，记忆一定会错。

```bash
# 装完立刻固化一份自己环境的快照（这就是你论文的"实现细节"）
pip freeze > env-lock.txt
nvidia-smi          # 记录驱动版本与 CUDA Version，论文里要写
```

### 三、环境踩坑清单（遇到就打勾）

- [ ] `torch` 与 `cuda` 版本不匹配
- [ ] `numpy` 版本冲突（2.x 与老代码不兼容）
- [ ] 缺少编译依赖（如 `gcc`、`ninja`）
- [ ] 数据路径写死在代码里，需要手动改
- [ ] 预训练权重下载超时（需换镜像源）

**报错要"三抄"**：

> 抄**报错原文**、抄**解决命令**、抄**一句话原因**。
> 攒够 20 条，你就有了自己的《复现踩坑手册》—— 这东西比论文本身值钱，因为它能复用。

记录格式建议就三列，写在 `论文精读/06-复现日志-day1.md` 里：

| 报错原文（关键一行） | 解决命令 | 一句话原因 |
|---|---|---|
| `ImportError: numpy.core.multiarray failed to import` | `pip install "numpy<2"` | 老代码用了 numpy 1.x 的私有 API |
| `CUDA error: no kernel image is available` | 重装对应 cu 版本的 torch | torch 编译的算力架构与本机 GPU 不匹配 |
| `FileNotFoundError: ./data/train.csv` | 改配置里的 `data_root` | 作者把绝对路径写死在 config 里 |

### 四、数据拿不到怎么办：三条替代路径

**数据拿不到是复现阶段的头号杀手**，尤其电力/工控数据大多不公开。按顺序试这三条：

```
1. 仿真生成   —— 能自己造出分布可控的数据，最可控，也最容易写进论文
2. 公开替代集 —— 换一个任务相近的公开数据集，先验证方法能不能跑
3. 联系作者   —— 邮件问，回复率不高但成本极低，顺手就发
```

第 1 条在电力场景里有现成工具：**pandapower** 可以几分钟跑通 IEEE 14 / 39 节点潮流计算，生成节点电压、支路功率等量测，再按需要注入坏数据。

### 五、和电网安全的关系

电网与工控领域的数据几乎不可能拿到真实生产环境版本 —— 涉及基础设施安全，公开数据集稀缺且规模小。这不是你运气差，而是**这个领域的客观约束**，也是你论文里必须交代清楚的一点。

由此产生两个直接影响你实验设计的结论：

1. **仿真数据是你的主战场。** 用 pandapower 生成量测，你才能完全控制攻击强度、注入位置、噪声水平，做出来的消融实验才有说服力。
2. **环境必须锁版本。** 潮流计算对数值精度敏感，`pandapower` 或 `numpy` 换个版本，节点电压的小数点后第 6 位就可能变，进而影响你构造的 FDI 攻击是否"满足物理约束"。**锁版本不是洁癖，是可复现性的硬要求。**

### 🔍 延伸思考

1. 如果作者提供的 `requirements.txt` 没有固定版本号（全是 `>=`），你今天装出来的环境和作者当初的环境还一样吗？你该怎么处理这个不确定性？
2. 用仿真数据做的实验，审稿人一定会问"仿真能代表真实电网吗"。你会怎么回答这个问题？（提示：从"结论是否依赖仿真的特定参数"这个角度想）

## Day 44 —— 跑通训练脚本：结果对不上的排查顺序

> **一句话**：结果对不上时，**不要乱试**。按"种子 → 数据划分 → 超参 → 指标 → 预处理 → 代码 bug"这个固定顺序查，因为 **80% 的"复现失败"死在前三条**。

### 一、先跑通，再跑准：最小配置策略

一上来就跑完整数据集 + 300 epoch，是最浪费时间的选择。正确做法是**先用最小配置验证管线通不通**：

```bash
# 大部分规范仓库都会留这种开关，没有就自己加一个
python train.py --debug --epochs 2 --subset 0.05 --batch_size 8
```

| 阶段 | 目的 | 配置 |
|---|---|---|
| **冒烟测试** | 管线能不能跑完一轮 | 5% 数据，2 epoch，小模型 |
| **快速验证** | 指标趋势对不对 | 30% 数据，20 epoch |
| **正式复现** | 对齐论文指标 | 全量数据，论文配置 |

**冒烟测试跑通的意义很大**：数据加载、前向、反向、评估、存盘这五件事全走了一遍，剩下的只是"跑得久"。

### 二、结果对不上的排查顺序（本节核心）

按这个顺序查，别跳步：

| 顺序 | 排查项 | 怎么查 | 经验占比 |
|---|---|---|---|
| 1 | **随机种子** | 换 3 个种子，看结果波动范围 | 前三条合计 |
| 2 | **数据划分** | 对比 train/val/test 切分方式与比例 | 吃掉 **80%** |
| 3 | **超参数** | lr、batch size、epoch 数是否与论文一致 | 的"复现失败" |
| 4 | **评价指标实现** | PR-AUC、F1 的宏/微平均是否算错 | |
| 5 | **数据预处理** | 归一化方式、缺失值填充是否一致 | |
| 6 | **代码本身有 bug** | 最后才怀疑，但也要怀疑 | |

**逐条展开：**

**① 随机种子 —— 先测出"波动范围"再谈复现**

这是最容易被忽略的一步。很多人拿一次运行的结果去对比论文，差 3 个点就慌了。正确做法是先固定数据划分、只换种子跑 3 次：

```
种子 42  → F1 = 0.901
种子 0   → F1 = 0.893
种子 123 → F1 = 0.912
波动范围：0.893 ~ 0.912（±1%）
```

**如果论文报 0.920，而你的种子间波动就有 ±1%**，那 0.912 和 0.920 的差距根本不算复现失败 —— 它在噪声范围内。**先建立"噪声标尺"，再判断差距是否有意义。**

**② 数据划分 —— 差异最隐蔽、影响最大**

| 陷阱 | 后果 |
|---|---|
| 用了随机切分，论文按时间切分 | 时序数据被随机切分 = **未来信息泄漏到训练集**，指标虚高一大截 |
| 类别比例不同 | 异常检测里正负样本比例变一点，PR-AUC 就能差 10 个点 |
| 验证集参与训练 | 早停用的是验证集，调参用验证集，最后报测试集 —— 顺序错了就废 |

> **时序数据的铁律：只能按时间切，不能随机切。** 电力负荷、报文序列都是时序数据，随机切分会让模型"看到未来"，指标好看但毫无意义。

**③ 超参数 —— 论文没写的那些才是坑**

论文正文往往只写"Adam, lr=1e-3"，但代码 config 里有 20 个参数。重点核对：`lr`、`batch_size`、`epoch`、`warmup`、`weight_decay`、学习率调度器的类型与触发点。

**④ 评价指标实现** —— 特别是 PR-AUC（不同实现插值方式不同）和 F1 的宏平均/微平均/加权平均。同一个模型，三种平均方式能报出三个不同的数。

**⑤ 数据预处理** —— 归一化用的是**训练集统计量**还是**全体数据统计量**？后者是典型的数据泄漏。缺失值填 0、填均值、还是前向填充，都会改变结果。

**⑥ 代码 bug** —— 放到最后不是因为它不可能，而是因为**前面五条更容易出错**。真要怀疑 bug 时，优先查：label 对齐、mask 位置、`dim` 参数方向、`zero_grad` 是否漏了。

### 三、复现失败的四类原因

| 类别 | 说明 | 能否解决 |
|---|---|---|
| **实现差异** | 作者代码与论文描述不完全一致 | 能，以代码为准 |
| **种子差异** | 随机性导致的结果波动 | 能，报均值±标准差 |
| **论文有误** | 论文写的数字本身有笔误或挑了最优 | 不能，但要记录下来 |
| **环境差异** | 框架版本不同导致数值行为不同 | 部分能，锁版本 |

> **"论文有误"也是结论。** 如果你认真排查后确认论文的数字复现不出来，这本身就是一条有价值的记录 —— 有些综述类工作专门做"复现性研究"。

### 四、必须完整记录的四件事

这四项直接对应论文里"Implementation Details"小节，现在不记，三个月后写论文时只能靠猜：

```
超参数：lr / batch_size / epochs / optimizer / scheduler / weight_decay
随机种子：torch.manual_seed / np.random.seed / random.seed / cudnn.deterministic
硬件环境：GPU 型号与显存 / CUDA 版本 / 驱动版本 / 训练时长
数据版本：数据集名称与版本 / 划分方式与比例 / 预处理脚本路径
```

**第一次成功跑通的日志一定要存好** —— 这是你的 baseline，后面所有改动都是跟它比。

### 五、和电网安全的关系

电网异常检测数据有两个特性，直接决定了"结果对不上"的高发：

1. **极端类别不平衡**：真实的 FDI 攻击样本可能不到 1%。这种情况下用准确率（Accuracy）评估毫无意义（全预测为正常就有 99% 准确率），必须用 PR-AUC、F1、召回率@固定误报率。**而不同实现对 PR-AUC 的处理方式不同，这是复现差异的重灾区。**
2. **时序强相关**：负荷曲线、量测序列都有日周期和趋势。**一旦用随机切分，模型会通过"记住未来"来作弊**，指标漂亮但工业场景直接失效。这就是为什么你的数据划分方式必须在论文里写清楚 —— 它决定了结果可不可信。

### 🔍 延伸思考

1. 如果换了 3 个种子，结果波动是 ±5%，而论文方法只比 baseline 高 2%，你还认为"方法有效"吗？这个实验该怎么重做？
2. 结果对不上时，怎么判断是代码问题还是论文本身有问题？（提示：能不能构造一个"最小可验证单元"来隔离问题？）

## Day 45 —— 读透源码：数据流追踪与隐式处理

> **一句话**：读懂源码的标志不是"每行都看懂了"，而是**能画出一张从原始数据到最终指标的数据流图**，并标出论文里没写、代码里却做了的那些"隐式处理"。

### 一、从入口文件开始追踪

不要从 `models/` 目录开始读，那是"从中间切进去"。正确路径是从入口往下追：

```
train.py / main.py          ← 入口：读参数、建数据、建模型、开训
   ↓
configs/*.yaml              ← 所有超参在这里，先看完它
   ↓
dataloader / dataset        ← 数据从哪来、怎么切、怎么变
   ↓
models/*.py                 ← 模型定义（前向长什么样）
   ↓
losses / metrics            ← 损失函数 + 评价指标
   ↓
trainer / engine            ← 训练循环、早停、存 checkpoint
```

**三处核心必看**：模型定义、损失函数、数据加载。其中**损失函数和评价指标是最容易埋坑的两处**。

### 二、画出源码数据流图

不要用文字描述，**画图**。一张 ASCII 图就够了：

```
原始数据 (csv/npy)
   │
   ├─[预处理] 归一化 / 缺失值填充 / 重采样      ← 隐式处理高发区
   │
   ├─[滑窗] window=100, stride=10               ← 决定样本数与 label 对齐方式
   │
   ├─[划分] train / val / test = 7:1:2（按时间）
   │
   ├─[DataLoader] batch_size=64, shuffle=True   ← 时序数据 shuffle 要小心
   │
   ├─[模型] Encoder → Latent → Decoder
   │
   ├─[损失] MSE + λ·正则项                      ← 论文只写了 MSE？
   │
   └─[评估] PR-AUC / F1 / 召回率@1%FPR          ← 实现方式必须核对
```

**在图上用另一种记号标出"这是我未来要改的地方"** —— 通常就是你的创新点落点：数据预处理方式、损失函数、模型中间某个模块。

### 三、最常见的论文-代码不一致

| 位置 | 论文可能没写 | 代码里却做了 |
|---|---|---|
| 数据 | 采样策略 | 过采样 / 欠采样 |
| 训练 | 早停条件 | 验证集指标不升就停 |
| 损失 | 各项权重 | 加了额外的正则项 |
| 评价 | 计算方式 | 用了点调整 / 滑动平均 |

**再补几条实战中高频出现的**：

| 位置 | 隐式处理 | 影响 |
|---|---|---|
| 数据 | 按类别做了平衡采样 | 指标显著虚高 |
| 模型 | 冻结了部分层不训练 | 参数量与训练时间对不上 |
| 训练 | 用了梯度裁剪 | 大 lr 也能训稳 |
| 评估 | 对异常分数做了滑动平均 | 平滑掉短时攻击，指标变好 |

> **这类差异必须逐条记录。** 你复现时如果没注意到，指标会差一大截，然后白白排查半天 —— 最后发现问题根本不在你的代码里，而在作者的代码里。

### 四、重点核对两处：损失函数与评价指标

**损失函数**：论文里写 `L = L_rec + λ·L_reg`，代码里可能是 `L = L_rec + λ·L_reg + μ·L_orth`。多出来的那一项，就是你复现不出论文指标的元凶。

```python
# 读源码时把损失函数逐项抄出来，标注每一项的权重
loss = mse(x_hat, x) * 1.0            # 重建损失
loss += torch.norm(z, p=1) * 1e-3     # ← 论文没写这条
loss += orthogonality_loss(...) * 0.1 # ← 论文也没写
```

**评价指标**：论文说"F1"，代码算的是 macro-F1 还是 micro-F1？论文说"PR-AUC"，用的是 sklearn 的 `average_precision_score` 还是自己写的梯形积分？**同一个模型，不同实现能差 5 个点。**

### 五、和电网安全的关系

电力异常检测的源码里，有两处"隐式处理"对结论影响特别大，必须在数据流图上标出来：

1. **滑窗与 label 对齐方式**。一个窗口内只要有一个时间步是攻击，就把整个窗口标为异常（window-level），还是逐时间步标注（point-level）？这两种标注方式下的指标**不可比**，而论文里往往只写"我们检测异常"。如果对齐错了，你会得到一个漂亮但完全虚假的指标。
2. **归一化统计量的来源**。如果用全体数据（含测试集）算均值和方差，测试集信息就泄漏进了训练。在电力场景里，量测的统计特性随季节、负荷水平变化，这个泄漏会显著抬高指标 —— 而工业部署时你根本拿不到未来数据的统计量。

2. 如果论文的损失函数里有一项你无法理解其作用，你会怎么验证它到底有没有用？（提示：这就是明天消融实验的雏形）

## Day 46 —— 复现的第一步改造：确认你能改代码

> **一句话**：复现的终点不是"跑通"，而是**你改了一行代码、指标动了、你能解释为什么动**。从这一刻起，你才从"使用者"变成"研究者"。

### 一、为什么"能改"比"能跑"重要

能跑通只说明你会用命令行。**能改代码并预测后果，才说明你理解了方法内部机制** —— 而论文的贡献一定来自某个改动。

改造的四个层次，由易到难：

| 层次 | 改什么 | 难度 | 是否可能成为创新点 |
|---|---|---|---|
| 1 | 换激活函数、调层数 | 低 | 一般不能 |
| 2 | 调损失函数权重、加正则项 | 中 | 可能是 |
| 3 | 替换某个模块的结构 | 中高 | 可能是 |
| 4 | 针对问题设计新机制 | 高 | 应该就是 |

**建议从层次 1 或 2 起步**，目标不是出成果，是**建立"我改代码 → 指标变化"的因果感知**。

### 二、推荐的第一次改造

```python
# 改造 A：换激活函数（一行）
- self.act = nn.ReLU()
+ self.act = nn.GELU()

# 改造 B：换损失函数，处理类别不平衡（几行）
- criterion = nn.BCEWithLogitsLoss()
+ pos_weight = torch.tensor([neg_count / pos_count])
+ criterion = nn.BCEWithLogitsLoss(pos_weight=pos_weight)

# 改造 C：调损失项权重
- loss = loss_rec + 1.0 * loss_reg
+ loss = loss_rec + 0.1 * loss_reg
```

每次只改一个变量。**同时改三个地方，指标变了你也不知道是谁的功劳。**

### 三、保证改动可回滚

改坏了要能退回去，这是底线：

```bash
git checkout -b exp/gelu-activation     # 每类改动开一个分支
git commit -am "exp: ReLU -> GELU"      # 改完就提交，commit message 写清改动
git diff main..exp/gelu-activation      # 随时能看清改了什么
```

没装 git 的项目，最低成本做法是**复制一份文件加后缀**（`model_gelu.py`），但强烈建议用 git —— 后面消融实验要做十几组，靠复制文件名会乱成一团。

### 四、判断改动是否"真的有道理"：三个检验

指标涨了不代表改动有效，可能只是噪声。过三道检验：

| 检验 | 怎么做 | 通过标准 |
|---|---|---|
| **1. 换种子重复** | 用 3 个种子各跑一遍 | 提升**稳定存在**，不是只在某个种子下有效 |
| **2. 多数据集验证** | 换一个数据集再跑 | 在另一个数据集上**也提升** |
| **3. 有理论解释** | 用一句话说清"为什么这样改会更好" | 能说清机制，不是"试出来的" |

> **三条全过 = 真发现；只过第一条 = 噪声。**
>
> 特别是第 3 条：如果只能说出"我试了一下发现它更好"，那这个改动**不能写进论文**。审稿人问"为什么"的时候，你答不上来就是致命伤。

### 五、和电网安全的关系

在电力异常检测任务上，"有道理的改动"通常来自**领域知识**，而不是网络结构的微调。举两个例子：

| 改动 | 理论依据 | 预期效果 |
|---|---|---|
| 损失函数里对漏报（FN）加大惩罚 | 电网场景**漏报一次攻击的代价远高于误报** | 召回率上升，误报率略升 |
| 在输入里加入物理约束残差 `r = z - H·x̂` | FDI 攻击的本质是让残差保持小值，残差是攻击者最想操纵的量 | 对隐蔽攻击更敏感 |

**这类改动的最大好处是"可解释"**：你不需要说"我试了很多次"，而是可以说"因为电网的漏报代价更高，所以我这样设计损失函数"。**领域知识驱动的改动，天然满足第 3 条检验。**

2. 如果换激活函数在数据集 A 上提升、在数据集 B 上下降，你会怎么解释？这个现象本身能不能写成论文的一部分？

## Day 47 —— 消融实验设计：先预测再跑

> **一句话**：消融实验的价值不在"跑了多少组"，而在**你有没有在跑之前写下预测** —— 预测这一列，是你理解深度的直接测量。

### 一、什么是消融实验

**消融（ablation）**：把模型的某个组件逐个拿掉，看性能掉多少，以此证明"这个组件确实在起作用"。

```
完整模型          → F1 = 0.92
去掉模块 A        → F1 = 0.87   （掉了 5 个点，A 很重要）
去掉模块 B        → F1 = 0.91   （掉了 1 个点，B 作用有限）
同时去掉 A 和 B   → F1 = 0.85
```

**"同时去掉"这一行很关键**：如果单独去掉 A 掉 5 点、单独去掉 B 掉 1 点，而同时去掉只掉 5.5 点，说明 **A 和 B 的功能高度重叠** —— 这是个值得写进论文的发现。

### 二、消融 vs 对比实验：两件不同的事

新手最常混的一对概念：

| 维度 | 消融实验（Ablation） | 对比实验（Comparison） |
|---|---|---|
| 比较对象 | **自己模型的内部组件** | **自己的方法 vs 别人的方法** |
| 回答的问题 | "我的模块有用吗？" | "我比 SOTA 好吗？" |
| 对照组 | 去掉某模块的自己 | baseline 方法 |
| 放在论文哪 | 消融小节 | 主结果表 |

**两者缺一不可**：对比实验证明"我更强"，消融实验证明"为什么我更值得更强"。

### 三、消融实验模板（照着填）

| 实验 | 改动 | **预测指标** | 实际指标 | 是否一致 |
|---|---|---|---|---|
| Full | 完整模型 | — | | — |
| w/o A | 去掉模块 A | | | |
| w/o B | 去掉模块 B | | | |
| w/o A+B | 同时去掉 | | | |

**"预测"这一列不能省。** 它强迫你在跑实验前先想清楚"每个模块为什么有用"：

- **预测全对** → 说明你真懂了模型的机制，可以放心往下写论文
- **预测错了** → 正好是学习的入口，说明你对某个机制的理解有偏差

> 一个实用的心理技巧：**预测要写得足够具体**（"去掉 A 后 F1 大概掉 3-5 个点，且误报率明显上升"），而不是"可能会变差"。模糊的预测等于没预测。

### 四、怎么设计 3 组有意义的对照

组数不用多，但每组要**对应一个可陈述的假设**：

| 组 | 假设 | 去掉后的预期 |
|---|---|---|
| 1. 去掉注意力模块 | 注意力负责捕捉长程依赖 | 长序列上的性能下降更明显 |
| 2. 去掉物理约束项 | 物理约束提升对隐蔽攻击的敏感性 | 在低强度攻击上漏报率上升 |
| 3. 去掉数据增强 | 增强缓解类别不平衡 | 少数类召回率下降 |

**注意第 1 组的设计巧思**：不要只看整体指标，要**分组看**（长序列 vs 短序列）。这样即使整体指标只掉 1 个点，你也能说出"它主要在长序列上起作用" —— 这比"掉了一个点"有信息量得多。

### 五、记录训练成本

除了指标，还要记录每个变体的成本：

| 实验 | 参数量 | 单 epoch 时间 | 推理时延(ms) | 显存(GB) |
|---|---|---|---|---|
| Full | | | | |
| w/o A | | | | |

**为什么必须记**：如果去掉 A 只掉 1 个点，但参数量减半、推理快 3 倍，那这个"去掉"可能反而是更好的方案 —— **工业场景里，性价比是硬指标**。

### 六、和电网安全的关系

消融实验在电网安全论文里有一个特殊作用：**证明你的方法不是靠"堆模块"**。

审稿人看到一篇论文用了 LSTM + 注意力 + 物理约束 + 对抗训练，第一反应是"这里面哪些是必要的？"。消融实验就是你回答这个问题的唯一工具。

更有价值的是**分场景消融**：不要只报整体 F1，而是按攻击强度分组：

| 攻击强度 | Full | w/o 物理约束项 | 差距 |
|---|---|---|---|
| 强攻击（Δz 大） | 0.95 | 0.94 | 1 点 |
| **弱攻击（Δz 小，隐蔽）** | **0.88** | **0.72** | **16 点** |

**这张表就是你论文最有力的论据** —— 它证明"物理约束项在隐蔽攻击场景下是必需的"，而不是"加了它整体好看一点"。整体指标会掩盖这种场景差异，所以**分组消融是电力安全场景的标配**。

### 🔍 延伸思考

1. 你的预测错了，说明你对哪个机制的理解有偏差？这个偏差会不会影响你论文里对方法的解释？
2. 如果两个模块单独去掉都掉很多，但一起去掉只多掉一点点，你会在论文里怎么写这个发现？

## Day 48 —— 换到电力场景数据：域偏移就是论文动机

> **一句话**：模型在新场景掉了 20 个点，**这不是失败，这是发现**。论文的 Introduction 就是靠这个数字讲出来的。

### 一、什么是域偏移

**域偏移（domain shift）**：训练数据（源域）与部署数据（目标域）的分布不一致。

```
源域：公开数据集（实验室采集 / 通用工业数据）
目标域：电力系统量测（含物理约束、极端不平衡、强时序相关）
         ↓
模型在源域学到的规律，在目标域不再成立
         ↓
性能下降 X%
```

**关键认知**：域偏移不是"你没调好参"，而是**数据分布本身变了**。再怎么调超参也解决不了。

### 二、三类域偏移（要能分清）

| 类型 | 定义 | 电力场景的例子 |
|---|---|---|
| **协变量偏移** | 输入分布 `P(x)` 变了，但 `P(y\|x)` 不变 | 训练用夏天负荷数据，部署在冬天 —— 负荷水平整体下移 |
| **标签偏移** | 标签分布 `P(y)` 变了 | 训练集攻击样本 10%，部署环境只有 0.1% |
| **概念偏移** | `P(y\|x)` 本身变了 | 同一条量测曲线，在 A 变电站是异常，在 B 变电站是正常工况 |

**分清类型的意义**：三类偏移的应对手段完全不同。协变量偏移可以用领域适应；标签偏移要重采样或调阈值；概念偏移最麻烦，通常只能重新标注、分场景建模。

### 三、定量测量性能下降

不要只说"效果变差了"，要**给出数字**：

```python
# 直接评估源域模型在目标域上的表现，不要重新训练
model.eval()                       # 注意：不要微调，要测"直接迁移"
with torch.no_grad():
    preds = model(target_X)
    f1_target = f1_score(target_y, preds, average="macro")

print(f"源域 F1: {f1_source:.3f}  目标域 F1: {f1_target:.3f}")
print(f"性能下降: {(f1_source - f1_target) / f1_source * 100:.1f}%")
```

**关键细节**：这里测的是 **zero-shot 迁移**（直接拿源域模型去目标域评估），不能先在目标域微调再测 —— 那就不是域偏移，是正常训练了。

### 四、分析性能掉在哪些样本上（论文动机的核心论据）

**只看整体下降幅度是不够的，必须做切片分析**：

| 切片维度 | 切法 | 想发现什么 |
|---|---|---|
| 按样本类别 | 正常 / 各类攻击 | 是不是某一类攻击完全失效 |
| 按攻击强度 | 强 / 中 / 弱 | 隐蔽攻击是不是重灾区 |
| 按时间位置 | 序列前段 / 中段 / 后段 | 长序列是不是更容易出错 |
| 按量测位置 | 关键节点 / 边缘节点 | 某些节点是不是天然难检测 |

**切片分析的结果就是你论文的核心论据**：不是笼统的"性能下降 20%"，而是"**性能下降主要集中在低强度隐蔽攻击上（下降 34%），原因是物理约束使得这类攻击在残差空间上几乎不可见**" —— 后者才是能支撑一篇论文的洞察。

### 五、性能下降就是你的论文动机

**这是本周最重要的一次视角转换：**

> 你原来的模型在新域上掉了 20 个点 —— **这不是失败，这是发现。**
>
> 论文的 Introduction 就该这么写：
>
> 1. 现有方法在标准数据集上表现良好
> 2. 但迁移到电力场景后，性能下降 X%
> 3. 原因是电力数据具有 Y 特性（物理约束 / 极端不平衡 / 时序强相关）
> 4. 因此我们提出 Z 方法
>
> **第 2 步和第 3 步的数据，就来自你今天的工作。**

| 你今天的"坏消息" | 转成论文里的"好消息" |
|---|---|
| 迁移后 F1 从 0.92 掉到 0.72 | Introduction 第 2 句：迁移到电力场景后性能下降 21.7% |
| 掉得最多的是隐蔽攻击 | Introduction 第 3 句：原因是物理约束使隐蔽攻击在残差空间不可见 |
| 你试了微调、领域适应都不够 | Related Work：现有方法无法解决该 gap |
| 你设计了一个新模块 | Method：我们提出 Z 方法 |

### 六、应对手段

| 手段 | 做法 | 代价 |
|---|---|---|
| **微调** | 用少量目标域数据继续训练 | 需要目标域标注数据 |
| **领域适应** | 对齐源域与目标域的特征分布（如 MMD、对抗训练） | 实现复杂，可能引入新超参 |
| **数据增强** | 按目标域特性改造源域数据（如注入电力物理约束） | 需要领域知识 |
| **重新设计** | 直接把领域特性写进模型（物理约束层） | 工作量大，但最可能是创新点 |

**注意最后一行**：如果前三条都不够，那就说明"现有方法无法直接迁移" —— **这正好是你提出新方法的合法性来源**。

### 七、和电网安全的关系

电力场景的域偏移有三个几乎无法回避的来源：

1. **物理约束**：电网量测必须满足潮流方程 `z = H·x + e`。通用异常检测模型没见过这种约束，会把"物理上不可能但统计上罕见"的量测当异常，也会漏掉"物理上自洽的 FDI 攻击"。
2. **极端不平衡**：攻击样本可能少于 0.1%。通用数据集没有这种比例，模型学不到决策边界。
3. **时序强相关**：负荷有日周期、周周期、季节周期。通用模型假设的 i.i.d. 样本在电力场景里完全不成立。

**这三条中的任何一条，都可以单独支撑一篇论文。** 你要做的不是三条都解决，而是**选一条讲透**。

### 二、选题写成一句话

选题必须能用**一句话**说清，包含三个要素：

```
针对【什么问题】，采用【什么方法】，因为【为什么可行】。
```

**示例**：

> 针对电力系统 FDI 隐蔽攻击检测中"物理约束导致残差不可见"的问题，采用**将潮流方程残差显式引入损失函数**的方法，因为该方法迫使模型学习物理不一致性而非统计离群性，从而对满足物理约束的攻击更敏感。

**说不清就是没想清。** 如果这句话你写不出来，说明"问题"和"方法"之间的逻辑链还没建立起来。

### 三、选题必须过四道关

| 关卡 | 标准 | 不过的后果 |
|---|---|---|
| 1. **真实存在的痛点** | 有文献或安全事件支撑，不是硬造的 | 审稿人："这个问题不存在" |
| 2. **已有方法解决不好** | 有 gap，且你能用数据说明 | 审稿人："用 XX 方法就够了" |
| 3. **你的方法有道理** | 能说清机制，不是堆模块 | 审稿人："为什么这样改会更好？" |
| 4. **实验能做完** | 数据、算力、时间都在掌控内 | **你自己做不完** |

> **第 4 条最容易被忽略。做不完的题目等于零。**
>
> 一个"理论上很漂亮但需要 8 卡 A100 训练两周"的选题，对你来说不是一个选题，是一个陷阱。**选题的约束条件是你自己的资源，不是论文的理想形态。**
