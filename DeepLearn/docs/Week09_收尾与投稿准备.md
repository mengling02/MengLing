## Day 57 —— 全文打磨：语言规范与引文检查

> **一句话**：好论文不是"写"出来的，是"改"出来的 —— 打磨分两条线：**语言规范**（读起来像论文）和**引文检查**（看起来像行家）。

### 一、语言规范：先删虚词，再统一术语

**第一刀：删掉虚词。** 学术写作的信息密度越高越好，虚词是纯噪声：

| 删掉 | 原因 |
|---|---|
| 其实、事实上 | 没有信息量 |
| 可能、大概、应该是 | 削弱结论的确定性（除非确实不确定） |
| 众所周知、不难发现 | 审稿人："那你还写它干什么" |
| 非常、十分、极其 | 形容词不提供证据，数字才提供 |
| 由于……的原因 | 语义重复 |

```
❌ 其实，众所周知，深度学习的方法可能大概能提升检测效果。
✅ 深度学习方法在隐蔽攻击场景下将 F1 从 0.830 提升至 0.923。
```

**第二刀：统一术语。** 同一个东西在全文只能有一种叫法：

| 不一致的例子 | 后果 |
|---|---|
| 前文"量测"，后文"测量值"，又出现"观测数据" | 读者以为是三个不同的东西 |
| 前文"检测器"，后文"检测模型"，又出现"判别器" | 审稿人质疑概念不清 |
| 缩写时用时不用（FDI / 虚假数据注入） | 阅读体验差 |

**做法**：列一张术语表，全文按它统一。这张表在投稿前再核对一遍。

**其余四条硬规范**：

| 规范 | 正确 | 错误 |
|---|---|---|
| **缩写首次出现给全称** | 虚假数据注入（False Data Injection, FDI） | 直接用 FDI |
| **数字与单位间加空格** | `5 ms`、`10 kV`、`3.2%` | `5ms`、`10kV` |
| **中英文标点不混用** | 中文用全角，英文用半角 | 中文句子里出现半角逗号 |
| **数学符号与正文分离** | 变量用斜体，单位用正体 | 变量用正体，单位用斜体 |

### 二、内容完整性：五项必查

| 检查项 | 标准 | 常见问题 |
|---|---|---|
| **图表编号与引用** | 每个图表都有编号、标题，且正文引用过 | 有图无引用（"孤图"） |
| **公式编号** | 每个独立公式有编号，正文有引用 | 公式编号跳号 |
| **参考文献格式** | 全文统一（同一套模板），无重复 | 同一篇论文被引了两次，编号不同 |
| **Related Work 时效性** | 必须有**近两年**的工作 | 最新引用是 3 年前的 |
| **图的分辨率** | 至少 **300 dpi** | 从 PPT 截图，放大就模糊 |

> **"孤图"是最常见的低级错误**：图放上去了，正文从头到尾没提过它。审稿人会直接指出"图 3 从未被引用"。**每个图表在正文里至少要出现一次。**

### 三、Related Work 的三个常见问题

| 问题 | 后果 | 改法 |
|---|---|---|
| 只引老论文 | 显得没跟进前沿 | 补近 2 年，尤其近 1 年 |
| 只罗列不评价 | 显得没思考 | 每段结尾加一句"但存在 X 不足" |
| 漏掉明显相关工作 | 审稿人认为你不知情 | 用它自己的引用网络反向找 |

**"只罗列不评价"的对照**：

```
❌ 文献 [3] 提出了基于 LSTM 的检测方法。[4] 使用了 CNN。[5] 使用了 Transformer。
   （读完不知道这些方法的优劣）

✅ 基于数据驱动的方法 [3-5] 摆脱了对物理模型的依赖，但均假设训练与测试
   数据同分布 —— 在电力场景的极端不平衡（攻击样本 < 0.1%）下，
   这些方法难以学到稳定的决策边界。
   （有分类、有评价、有指向自己的 gap）
```

> **引文检查的笨办法最有效**：打开你引用的每篇论文的 **References**，
> 扫一遍有没有你该引却没引的 —— 这个方法能抓住 80% 的漏引。

### 四、和电网安全的关系

电网安全方向的论文，有两个语言层面的坑特别容易踩：

**① 术语的领域含义与通用含义不同。**

| 词 | 通用 AI 论文里的意思 | 电力系统里的意思 |
|---|---|---|
| **状态** | 隐变量 / hidden state | 节点电压幅值与相角（一个明确的物理量） |
| **观测** | observation（强化学习里的） | 量测量（SCADA 采集的数据） |
| **攻击** | adversarial attack（扰动输入） | 可能是物理入侵、也可能是数据篡改 |
| **鲁棒性** | 对抗鲁棒性 | 可能是 N-1 安全（一条线路断开后系统仍稳定） |

**"鲁棒性"这个词尤其危险** —— 电力审稿人可能理解成"N-1 安全分析"，AI 审稿人理解成"对抗鲁棒性"。**第一次出现时必须明确限定**（写"对抗鲁棒性"而不是"鲁棒性"）。

**② 引文要覆盖两个圈子。** 一篇电网 + AI 的论文会同时被电力背景和 AI 背景的审稿人看。**Related Work 里必须两条线都有**：

```
电力安全线：Liu et al. 2009（FDI 奠基）→ 残差检验类方法 → 近年电力场景的检测工作
AI 安全线：对抗攻击（FGSM / PGD）→ 异常检测 → 工控场景的对抗样本研究
```

**只引一条线，另一边的审稿人会认为你"不了解相关工作"** —— 这是交叉方向论文最常见的拒稿理由。

### 🔍 延伸思考

1. 你的 Related Work 里，"已有工作的不足"这一段，是否真的指向了你方法要解决的问题？还是只是泛泛而谈？
2. 如果你的论文被两个不同背景的审稿人看，你猜他们各自最可能质疑哪一点？你现在的稿子能回应吗？

## Day 58 —— 投稿目标调研：期刊选择与格式要求

> **一句话**：选刊不是"挑最好的投"，而是**在匹配度、周期、难度之间找最优解** —— 投错刊浪费的是三个月，不是三小时。

### 一、期刊 vs 会议

| 维度 | 期刊（Journal） | 会议（Conference） |
|---|---|---|
| **审稿周期** | 长（3-12 个月） | 短（2-4 个月出结果） |
| **审稿方式** | 一轮轮修改（大修/小修） | 一次性决定（接收/拒稿） |
| **修改机会** | 有，可以反复改 | 基本没有，被拒就是被拒 |
| **评价体系** | 影响因子、中科院分区 | CCF 分级（A/B/C） |
| **适合阶段** | 工作较完整、需要打磨 | 需要快速拿到成果、时间紧 |

**给你的建议**：研究生第一篇论文，**会议出结果快，适合快速积累**；如果工作扎实且不赶时间，**期刊的"大修"机会反而是好事**（能按审稿意见改，比一次性被拒强）。

### 二、国内评价体系

| 体系 | 是什么 | 用在哪 |
|---|---|---|
| **中文核心** | 北大核心 / CSCD / 科技核心 | 中文期刊的评价标准 |
| **CCF 分级** | 中国计算机学会推荐目录（A/B/C 类） | 计算机领域会议的权威分级 |
| **中科院分区** | 按影响因子把期刊分 1-4 区 | 国内高校/科研院所普遍采用 |

**这三套体系的用途不同**：CCF 分级主要针对计算机领域的**会议**；中科院分区主要针对**期刊**。你投会议看 CCF，投期刊看分区。

### 三、投稿目标评估表

| 候选 | 类型 | 匹配度 | 审稿周期 | 录用难度 | 格式要求 |
|---|---|---|---|---|---|
| 候选 1 | | | | | |
| 候选 2 | | | | | |
| 候选 3 | | | | | |

**"匹配度"怎么判断**：翻目标期刊/会议近两年的论文，问自己三个问题：

```
1. 有没有 3 篇以上和我方向接近的论文？（有 → 匹配度高）
2. 它们的方法复杂度和我差不多吗？（差太多 → 你可能够不着，或显得太简单）
3. 它们的实验规模（数据集数、baseline 数）我能达到吗？
```

**第 3 条最实用**：如果目标期刊的论文都做了 5 个数据集、10 个 baseline，而你只有 2 个数据集、4 个 baseline，**录用概率很低** —— 这不是质量问题，是"门槛问题"。**先投门槛匹配的，第二篇再冲。**

### 四、必须自己到官网核实的三件事

> **这三条我无法替你确认（信息会随年份变化），你必须自己去官网核对。**

| 事项 | 为什么要查 | 去哪查 |
|---|---|---|
| **刊号 / 会议全称** | 别写错，也别凭印象写 | 期刊官网 / 会议官网 |
| **是否在预警名单上** | 某些期刊被列入预警，**投了不算成果** | 中科院文献情报中心《国际期刊预警名单》 |
| **格式模板下载地址** | 排版必须用官方模板 | 官网投稿系统，**不要用第三方站** |

**"投了不算成果"这件事的代价**：有些单位在评奖、毕业审核时会剔除预警期刊上的论文。**花十分钟核实，避免三个月白干。**

### 六、和电网安全的关系

电网 + AI 这个交叉方向，投稿目标大致有三类，各有取舍：

| 类型 | 代表方向 | 优势 | 劣势 |
|---|---|---|---|
| **电力/能源类期刊** | 电力系统自动化、电网技术、IEEE TSG / TPS | 领域认可度高，审稿人懂物理约束 | 对电力系统知识的深度要求高，AI 方法的新颖性权重低 |
| **计算机/安全类会议** | CCF 推荐的网络与信息安全会议 | 认可 AI 方法的新颖性 | 审稿人可能不熟悉电力物理约束，需要更多解释 |
| **交叉/综合类期刊** | 能源信息学、工控安全类期刊 | 匹配度天然高，开放获取多 | 影响因子可能偏低 |

**选择建议**：**优先看"你的核心创新点落在哪一边"**。

- 创新点在**物理约束的建模方式** → 投电力类，审稿人能欣赏
- 创新点在**检测算法本身** → 投计算机/安全类
- 两边都有 → 投交叉类，匹配度最高

**不要为了"冲高分"投一个完全不匹配的刊** —— 大概率是"不送审直接拒"（desk reject），白等一个月。

### 🔍 延伸思考

1. 如果目标期刊要求"与已有方法对比至少 5 个 baseline"，而你现在只有 3 个，你会换刊还是补实验？补实验需要多久？
2. 你会怎么判断一个期刊"是不是水刊"？（提示：看审稿周期、看论文质量的方差、看是否被列入预警名单）

## Day 59 —— 代码整理与复现说明：可交付的 GitHub 仓库

> **一句话**：审稿人要求提供代码时，**你的仓库要能"陌生人按 README 走一遍就跑通"** —— 这是从"我的代码"到"可交付成果"的分水岭。

### 一、仓库目录结构

```
project/
├── README.md            # 必读：环境依赖 / 数据准备 / 训练命令 / 预期结果
├── requirements.txt     # 固定版本号
├── LICENSE              # 学术项目通常 MIT 或 Apache-2.0
├── .gitignore           # 排除数据、权重、日志
├── configs/             # 超参配置（yaml/json）
├── data/                # .gitignore 掉，只留 README 说明格式
├── models/              # 模型定义
├── utils/               # 工具函数（数据加载、指标、可视化）
├── train.py             # 训练入口
├── eval.py              # 评估入口
└── scripts/             # 一键复现脚本
```

**`scripts/` 目录是关键**：写一个 `reproduce.sh`，把所有实验一条命令跑完：

```bash
#!/usr/bin/env bash
set -e
python train.py --config configs/main.yaml --seed 42
python train.py --config configs/main.yaml --seed 0
python train.py --config configs/main.yaml --seed 123
python eval.py --config configs/main.yaml --report results/main.csv
```

**审稿人/读者最想看的就是这个文件** —— 他不想读你的 20 个参数，他想"一条命令跑出论文的表格"。

### 二、README 必须写清四件事

| 部分 | 内容 | 常见缺失 |
|---|---|---|
| **环境依赖** | Python 版本、CUDA 版本、`pip install -r requirements.txt` | 没写 Python 版本 |
| **数据准备** | 数据从哪来、放哪个路径、什么格式 | 只说"准备好数据"，不说格式 |
| **训练命令** | 完整可复制的命令（含参数） | 命令里有占位符没说明 |
| **预期结果** | 跑完应该得到什么指标 | 没有预期结果 → 读者不知道是否成功 |

**"预期结果"这一项最容易被忽略，但最重要**：如果 README 里写"训练约 2 小时后，测试集 F1 应达到 0.92 ± 0.01"，读者就能自己判断有没有跑对。**没有这个数字，读者跑出来 0.85 也不知道是环境问题还是正常波动。**

### 三、依赖固定：不要用 `>=`

```
❌ 差：torch>=2.0
✅ 好：torch==2.1.2

❌ 差：numpy
✅ 好：numpy==1.26.4
```

**为什么要精确到补丁版本**：`numpy` 1.x 到 2.x 是一次破坏性升级，老代码直接报错。`torch` 的次版本之间也可能有数值行为差异。**"我这儿能跑"的承诺，只能靠固定版本号兑现。**

生成方式：

```bash
pip freeze > requirements.txt     # 从你验证过的环境导出
```

### 四、上传前必做的三件事

> **这三件事没做，上传后基本无法挽回。**

| 检查 | 内容 | 后果 |
|---|---|---|
| **1. 硬编码本地路径** | 搜 `C:\Users`、`/home/xxx`、`D:/` | 别人跑不了，暴露你的目录结构 |
| **2. 敏感信息** | API key、密码、数据库连接串、**内网 IP** | 安全事故 |
| **3. 不该公开的数据** | 真实电力数据、客户数据、未脱敏数据 | 合规与法律风险 |

```bash
# 上传前先搜一遍（在仓库根目录执行）
grep -rn "C:\\\\Users\|/home/\|api_key\|password\|192\.168\.\|10\.0\." --include="*.py" --include="*.yaml" .
```

> **GitHub 上删掉的文件仍在历史记录里。** 上传前检查比事后删除容易得多 —— 事后清理需要重写 git 历史（`filter-repo`），风险高且可能已经泄漏。

### 五、和电网安全的关系

**电力 + AI 项目的代码开源，有一条额外的红线：不能泄漏任何真实电网信息。**

需要逐项检查的内容：

| 类别 | 具体内容 | 为什么敏感 |
|---|---|---|
| **网络拓扑信息** | 变电站名称、线路编号、真实节点连接关系 | 属于关键基础设施信息 |
| **内网地址** | SCADA / RTU 的 IP、端口、通信协议配置 | 直接构成攻击面 |
| **真实量测数据** | 生产环境的电压、电流、功率记录 | 可能反推运行状态 |
| **设备指纹** | 厂商型号、固件版本、通信规约版本 | 便于攻击者匹配已知漏洞 |
| **攻击脚本** | 针对真实系统的注入脚本 | 可能被直接滥用 |

**处理原则**：

```
1. 全部用公开标准算例（IEEE 14 / 39 / 118 节点），不用任何真实拓扑
2. 攻击脚本只针对仿真环境，且在 README 里明确声明用途限于研究
3. 数据目录用 .gitignore 排除，只提交数据格式说明与生成脚本
4. 提交前用 grep 扫一遍敏感关键词（内网网段、设备型号、厂商名）
```

**这不只是"合规"，也是审稿人关心的问题** —— 如果你的仓库里有真实电网数据，审稿人会质疑数据来源的合法性。**用仿真数据 + 开源生成脚本，既安全又完全可复现，是双赢。**
