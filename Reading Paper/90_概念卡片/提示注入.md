# 提示注入

## 一句话

把恶意指令藏进大模型的输入里，让模型**把数据当成命令执行** —— 用户只是想让它总结一份文档，它却照着文档里的话去调工具、改参数。

## 为什么重要

电网正在把[[大语言模型(LLM)]]往业务里塞：故障诊断（把告警文本喂给模型让它判断故障类型）、调度辅助（让它读规程和运行数据给建议）、攻击检测解释（让它解释告警为什么可疑）。一旦 LLM 从"聊天"走向"接工具、读实时数据、下建议"，它就从一个信息工具变成了**一个有执行能力的组件**。

提示注入之所以值得单独建卡，是因为它是 LLM 应用**结构性、无法靠打补丁消除**的缺陷：LLM 的输入通道（用户输入、检索到的文档、工具返回、日志、传感器读数）在模型眼里**没有"数据"和"指令"的语法区分**，全都是 token 序列。这跟 SQL 注入有本质区别 —— SQL 注入的根因是"拼接字符串"，只要改成参数化查询就能根治；而提示注入没有等价的"参数化查询"，因为模型必须理解自然语言才能工作。

对电网的含义很直接：如果调度辅助智能体能读 SCADA 日志，那么**一条被攻击者精心构造的告警文本，就是一次远程指令注入**。

## 核心要点

| 分类维度 | 类型 | 说明 |
|---|---|---|
| 注入通道 | 直接注入 | 攻击者直接是用户，在对话框里输入恶意指令（越狱 jailbreak 常归此类） |
| | 间接注入 | 恶意指令藏在模型会读取的外部内容里（网页、PDF、邮件、日志、代码注释） |
| | 多模态注入 | 藏在图片、音频里（见多模态 LLM 的扩展攻击面） |
| 攻击目标 | 劫持输出 | 让模型说出攻击者想要的内容（虚假处置建议、错误诊断） |
| | 劫持工具调用 | 让智能体去调用某个工具/接口，形成实际的越权操作 |
| | 数据外泄 | 诱导模型把上下文中的敏感信息带出来 |
| | 绕过安全策略 | 让模型无视系统提示词里的约束 |
| 常见手法 | 指令覆盖、角色扮演、编码混淆、分隔符逃逸 | 具体写法迭代很快，属于"军备竞赛"型问题 |
| 防御思路 | 输入过滤/隔离、权限最小化、工具白名单、双模型校验 | 目前没有能彻底解决的方案，业界共识是"纵深防御 + 限制爆炸半径" |

## 关键公式

这个概念以定性描述为主，没有单一的核心公式。它的技术要点可以概括为一条"信任边界"判断：

- **同一上下文窗口内的内容，信任级别是相同的。** 无论这段文字来自用户、来自检索库、还是来自被攻击的日志文件，模型都只能靠语义去猜"这算不算指令"。
- 因此工程上的核心问题不是"如何过滤掉坏指令"，而是**"如何让模型即使被骗，也做不出危险动作"** —— 即把安全边界从"模型判断"下移到"系统权限控制"。

换句话说，提示注入的防护哲学和你熟悉的**不可信输入处理**一致：不要试图枚举所有恶意输入，而是让不可信输入永远无法直接触达危险操作。

## 用网安的话说（小电解读）

你可以把它理解成 **LLM 版的命令注入 / 跨站脚本**：

- 和**命令注入**相同的地方：都是"把数据当代码执行"。攻击者不攻破程序，只是让程序自己把恶意内容当命令跑起来。
- 和 **XSS** 更神似：XSS 的根因是"浏览器无法区分页面里的数据与脚本"，提示注入的根因是"LLM 无法区分上下文里的数据与指令"。所以提示注入常被戏称为 "LLM 的 XSS"。
- 关键不同点：SQL 注入/命令注入有结构性修复（参数化、白名单转义），**提示注入没有**。因为自然语言的"语义边界"无法用语法规则精确界定。这意味着它更像**社会工程学** —— 你防的是"说服"，而不是"语法绕过"。

电网场景的特殊之处，也是这个方向最值得做的点：

1. **间接注入通道天然存在且不可控**。电网里的文本来源极杂：设备告警、运维工单、厂商说明书、检修记录、第三方数据。任何一条都可能被注入，而运维人员根本不会去审查"这条告警里有没有藏指令"。
2. **爆炸半径极大**。IT 场景里 LLM 被劫持，最坏是"回复了错误信息"；电网场景里如果智能体连着控制/调度接口，最坏是**下发错误控制指令**。所以电网 LLM 应用必须做**权限隔离**：读的模型和写的通道彻底分开，模型只能建议、不能执行。
3. **数据外泄路径特殊**。模型上下文里可能有拓扑、量测、客户信息，一旦被诱导输出，等于把[[电力信息物理系统(CPS)]]的内部状态直接送出去。

切入建议：这个方向在电网文献里还很新。一个具体可做的题目是"给电网 LLM 应用做提示注入的红队测试"——构造藏在告警文本/工单里的注入样本，看智能体会不会调用不该调用的工具。门槛低、结论直观、和你的网安背景完全对口。
