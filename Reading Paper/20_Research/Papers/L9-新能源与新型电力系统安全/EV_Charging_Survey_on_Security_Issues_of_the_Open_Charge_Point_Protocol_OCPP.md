# 084 | 电动汽车充电：开放充电点协议（OCPP）安全问题与挑战综述

> [!abstract] 一句话
> 全球充电桩互联用的 OCPP 协议，**直到 2.0 版本才加入安全机制**——之前版本基本是"明文 + 弱认证"，这篇把它的问题和已有方案梳理了一遍。

## 为什么读它

**这篇是你的"协议安全"技能在电网领域的第一个落点。**

你学过认证协议、做过协议分析。OCPP 就是一个**正在大规模部署、但安全设计严重滞后**的应用层协议——这种"协议已经铺开了、安全问题还没解决"的状态，正是协议安全研究最有价值的时机。

读它的三个理由：

1. **它是"入门"难度，读起来最轻松**。综述性质，不需要控制理论、不需要电力系统背景。
2. **它的攻击面你完全熟悉**：中间人、重放、身份伪造、降级攻击、明文嗅探。这些在 IT 协议里你都见过，只是换到了"充电桩 ↔ 充电桩管理系统"这个场景。
3. **它的现实紧迫性强**。电动汽车和充电桩在中国增长极快，充电桩本身就是**大功率负载**——大量充电桩被同时操纵，对配电网的影响是实打实的。而**山东是电动汽车保有量和充电设施建设的大省**，这个场景离国内实践很近。

一句话定位：**084 是"协议安全"在新能源领域的入口，也是你最容易上手写第一篇论文的题材。**

## 这篇论文在讲什么（白话版）

### 背景：电动汽车充电是一个"多方通信"场景

论文开篇讲了一个简单的趋势：**智能电动汽车（EV, Electric Vehicle）和插电式电动汽车（PEV, Plug-in Electric Vehicle）** 的普及，催生了一个新的研究和开发领域。**住宅区和公共区域的电动汽车充电点数量大幅增加。**

数量增加带来的直接问题是：**在这些充电站点内，各种实体（entities）需要以安全且高效的方式通信。**

先搞清楚有哪些"实体"。一个 OCPP 场景里的角色主要有：

- **电动汽车（EV）本身**：车载电池管理系统（BMS）和充电控制单元。
- **充电桩 / 充电点（Charge Point, CP）**：就是物理上的充电设备，负责和车通信、控制充电功率。
- **充电站管理系统（CSMS, Charging Station Management System）**：后端的"大脑"，管理成千上万个充电桩——负责计费、授权、负载控制、固件升级。
- **用户 / 移动 App**：车主通过 App 找桩、启动充电、付费。
- **电网 / 配电运营商**：关心的是充电负荷对配电网的影响。

**这些角色之间要通信**：车要告诉桩"我能接受多大电流"，桩要问后端"这张卡能充吗"，后端要告诉桩"现在电网紧张，限制功率"，用户 App 要查"充了多少电、多少钱"。

**OCPP（Open Charge Point Protocol，开放充电点协议）** 就是用来协调这些通信的协议。论文指出：**它已经在许多实现中被使用（already being used in many implementations）**——也就是说，这不是一个实验室协议，是**事实上（de facto）的行业标准**。

### 核心问题：安全机制来晚了

论文最重要的一句话是：

> **只有最新的 OCPP 2.0 版本才包含某些安全特性（only the latest OCPP 2.0 version of the protocol includes certain security features）。**

这句话的分量很大。翻译成大白话：

- OCPP **1.5、1.6** 这些早期版本（也是目前部署量最大的版本）**基本没有内置安全机制**。
- 通信通常是 **WebSocket 上的明文 JSON**——数据在网络上裸奔。
- 认证机制很弱，很多实现靠**充电桩的序列号**或者**静态密钥**做身份识别，而这些信息一旦泄露就无法更换。
- **没有端到端加密，没有消息签名，没有防重放机制。**

这就意味着：**一个能接触到网络的人（比如同一个 Wi-Fi 下、或者在运营商网络内部）就可以监听甚至篡改充电通信**。

**这个状态在 IT 里你非常熟悉**——它就像**早期的 Modbus/TCP、早期的 SNMP、早期的 Telnet**：协议设计时只考虑功能，安全是后来才补的，而补的时候已经有几百万台设备在跑了，改不动。

### 论文做了什么

论文的工作是标准的综述结构，分四步：

**第一步：梳理 OCPP 场景中的实体（entities）。** 也就是上面说的那些角色——充电桩、后端系统、车辆、用户。论文明确界定了每个实体的角色和它们之间的信任关系。

**第二步：识别安全问题和威胁（security issues and threats）。** 论文系统梳理了 OCPP 面临的安全威胁。虽然没有在摘要中列举具体威胁清单（摘要未给出具体威胁条目），但从"OCPP 1.6 无安全机制"这个前提可以推断，威胁必然包括：通信窃听、消息篡改、身份伪造、重放攻击、拒绝服务、未授权访问充电桩等。

**第三步：整理学者们已经提出的解决方案（solutions that have been proposed by scholars）。** 论文不是只指出问题，还汇总了学术界的应对方案。这是综述的价值——**它告诉你"哪些问题已经被解决了、怎么解决的"**。

**第四步：指出仍未解决的安全问题，并提出未来研究方向。** 这是综述最有价值的部分：**它明确告诉你空白在哪里**。

### 论文的结论

论文识别出了 OCPP 的**开放安全问题（open security issues）**，并提出了**协议安全增强的未来研究方向**。

## 关键公式（小白版）

这篇以协议综述为主，没有需要展开的核心公式。

它的技术路线是：**界定 OCPP 生态中的实体与信任关系 → 梳理协议各版本的安全能力差异 → 识别安全威胁 → 汇总已有解决方案 → 指出开放问题与未来方向**。

如果你需要理解协议层面的技术细节，最相关的是**认证与防重放的通用结构**。任何挑战-应答（challenge-response）认证的基本形式是：

$$\text{Verify}\Big( \text{Response}, \ \text{Challenge}, \ K \Big) = \text{true}$$

- $\text{Challenge}$：验证方发的一次性随机数（nonce）。
- $\text{Response}$：被验证方用共享密钥 $K$ 对挑战值计算出的应答（通常是 HMAC 或签名）。
- $K$：只有合法双方知道的密钥。
- $\text{Verify}(\cdot)$：验证函数。

**这个公式在说什么**：**挑战值每次不同，所以攻击者即使截获了上一次的应答，也无法重放**——因为这次的挑战值变了，旧应答对不上。这是防重放攻击的标准手段。OCPP 2.0 引入的安全机制本质上就是补上了这一层（以及 TLS 传输加密）。

## 用网安的话说（小电解读）

**这篇论文你几乎不用"翻译"——它本身就是协议安全的内容，只是应用场景换成了充电桩。**

对齐到你的知识体系：

- **OCPP ≈ 一个明文/弱认证的应用层协议（像早期 Modbus）**。这是最贴切的类比。共同特征：
  - 设计时优先考虑**功能互操作性**，安全是事后补的
  - 认证靠**静态标识符**（序列号、静态密钥），泄露即失陷
  - 传输层明文或弱加密
  - **部署规模巨大，导致"改协议"的成本极高**（兼容性包袱）
  
  **这类协议的典型攻击套路你完全清楚**：中间人（MITM）、重放（replay）、降级攻击（downgrade，迫使双方用不安全的旧版本）、身份伪造（spoofing）、消息注入。

- **"只有 2.0 才有安全特性" = 版本降级攻击的温床**。这是一个非常关键的点。**当一个协议的旧版本不安全、新版本安全，而协议允许协商版本时，攻击者就可以在握手阶段强制双方回退到旧版本。** 这是 TLS 历史上反复出现的问题（POODLE、FREAK、Logjam 都是降级攻击）。**OCPP 的版本共存期正是这类攻击的高发期。**

- **攻击的物理后果 ≠ 传统 IT**。这是电力和 IT 的关键差异，必须记住：
  - 篡改充电功率指令 → **可以造成配电网过载**
  - 同时操纵大量充电桩 → **可以制造或消除负荷尖峰**（这正是第 085、087 篇的主题）
  - 伪造计费数据 → **直接经济损失**
  - 非法解锁充电枪 → **物理安全风险**
  
  **在 IT 里，协议被攻破的后果是"数据泄露"；在这里，后果是"配电网过载"或"设备损坏"。**

- **可迁移的选题（这篇的选题空间非常大）**：
  1. **OCPP 的安全形式化分析**：用形式化方法（如 ProVerif、Tamarin、Scyther）对 OCPP 的认证协议建模，**自动搜索攻击路径**。这是你的"协议安全"技能的直接应用，而且 OCPP 的形式化分析文献相对少。**门槛适中、创新点清晰、评价客观（能不能找到攻击）。**
  2. **OCPP 版本降级攻击**：专门研究 OCPP 1.6 与 2.0 共存时的降级攻击路径。这是一个非常具体、非常实际的题目。
  3. **大规模充电桩被控的物理影响**：把"协议被攻破"和"配电网影响"连起来——**攻击者控制 N 个充电桩能造成多大的负荷扰动**？这直接对接第 087 篇（负载改变攻击）的思路。
  4. **充电桩固件逆向**：充电桩是一个嵌入式 Linux 设备，跑着 OCPP 客户端。**用你的逆向技能挖真实设备的漏洞**，是很扎实的工作。

## 局限性

- **综述性质，缺乏原创技术贡献**。论文的价值在于梳理和组织，不在于提出新方法。你不能从它这里学到具体的技术方案。
- **时间较早（2022 年 7 月）**。OCPP 2.0.1 在 2022 年后持续演进，充电桩安全领域也在快速发展。这篇综述可能没有覆盖最新的协议特性和攻击研究。
- **偏协议层面，缺实证**。论文梳理的是"文献中提出的方案"，但**没有自己搭建测试床去验证这些攻击是否真的可行**。这是综述的固有局限，但意味着攻击的可行性仍需实证（对比第 086 篇 ChargeX，那是真刀真枪做了硬件实验的）。
- **未深入讨论物理影响**。论文聚焦于协议安全，对"协议被攻破后对配电网造成什么物理影响"讨论较少。而这恰恰是电力安全研究最关心的部分。
- **对 PKI 和密钥管理的落地难度讨论不足**。OCPP 2.0 引入安全机制依赖证书体系（PKI），但**在跨运营商、跨厂商、跨国的充电网络里部署 PKI 是极其困难的工程问题**（谁做 CA？证书怎么吊销？互操作性怎么保证？）。论文提到了方向，但没有深入。
- **摘要未给出具体威胁清单**。摘要只说"识别安全问题与威胁"，没有列出具体条目，需要读全文。

## 和你的方向有什么关系

- **这是 L9 里你"上手成本最低、最可能快速出成果"的一篇**。因为你不需要学控制理论、不需要学电力系统动力学，**你需要的是你已经会的协议分析能力**。
- **最推荐的选题**：
  1. **OCPP 的形式化安全分析**（最推荐）。用 ProVerif/Tamarin 对 OCPP 的认证和密钥协商流程建模，搜索攻击路径。这是**方法成熟、工具现成、评价客观**的题目，而且 OCPP 的形式化分析文献不多。

  3. **充电桩固件逆向与漏洞挖掘**：充电桩是嵌入式设备，固件可提取、可分析。这是一个很实在的工程题。
- **和你实验室方向的对接**：
  - **"协议安全"** → OCPP 形式化分析、降级攻击
  - **"程序逆向"** → 充电桩固件分析、协议实现漏洞挖掘
  - **"AI 与数据安全"** → 充电桩流量异常检测（OCPP 消息序列的异常检测，用 LSTM/Transformer 建模正常的充电会话流程）
  - **"工业 AI 与智能体"** → 用智能体模拟充电桩攻击/防御博弈
- **地域上**：山东是新能源汽车和充电设施建设的大省，城市级充电网络的规模很大；贵州则在推进新能源汽车下乡和高速服务区充电覆盖。**如果要做真实场景的充电桩安全测试，国内有大量可接触的样本**——而且充电桩安全在国内受到的关注度还不够高，这是一个很好的时间窗口。
- **一个提醒**：做充电桩安全研究要注意**法律和授权边界**。测试真实充电桩必须获得授权，建议优先在实验室搭建测试床或者使用开源实现。

## 原文摘要

> The increased use of smart Electric Vehicles (EVs) and Plug-in Electric Vehicles (PEV) opened a new area of research and development. The number of EV charging sites has considerably increased in residential as well as in public areas. Within these EV charging sites, various entities need to communicate in a secure and efficient way. The Open Charge Point Protocol (OCPP) offers a way to coordinate this communication and is already being used in many implementations. However, only the latest OCPP 2.0 version of the protocol includes certain security features. In this article, we present the entities that take part in an OCPP-based smart charging scenario, we identify security issues and threats and present solutions that have been proposed by scholars.We identify open security issues for OCPP and propose future research directions for the security enhancement of the protocol.
