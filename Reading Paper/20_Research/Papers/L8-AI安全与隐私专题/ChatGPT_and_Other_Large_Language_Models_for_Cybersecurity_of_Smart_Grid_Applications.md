# 073 | ChatGPT 等大语言模型用于智能电网应用的网络安全

> [!abstract] 一句话
> 把大语言模型（ChatGPT 等）用来看守数字变电站里的 IEC 61850 通信报文，判断 GOOSE 和 SV 这些组播消息是否异常，并在框架里首次引入了"人工在环"训练——把人类专家的安全指南喂给模型。

- **这是 L8 里两篇 LLM 论文的第一篇**，定位是**"把 LLM 当作安全检测工具"**——即考察 **LLM 的安全能力**。
  - 注意与 L5 层（034–037）的区别：**L5 是"用 LLM 做电网任务"**（比如用 LLM 理解电网文档、辅助调度），**L8 这两篇（073、074）是"把 LLM 用在安全任务上"**，问题意识是安全的，不是电力的。

## 这篇论文在讲什么（白话版）

### 背景：数字变电站的通信安全

论文的出发点是：**针对变电站（electrical substation）的网络攻击，对电网的完整性构成重大威胁**，因此需要全面的防御与缓解策略。论文特别强调：

> **信息与通信技术（Information and Communication Technology, ICT）中的任何异常，都应该被检测出来**，以保证数字变电站内设备之间的通信安全。

**先补三个电网概念（这是读懂本文的关键）：**

**（1）数字变电站（Digital Substation）**：传统变电站的保护和控制靠大量铜缆硬接线；数字化之后，一次设备的电流电压被**采样**成数字信号，通过**以太网**在站内设备间传输。好处是省线缆、灵活；代价是**把攻击面从物理层搬到了网络层**。

**（2）IEC 61850**：这是变电站自动化的国际通信标准。它规定了站内设备怎么通信、数据怎么建模。你在网安里熟悉的"协议就是攻击面"的逻辑在这里完全适用——**只要攻击者能伪造或篡改 IEC 61850 报文，就能操纵变电站的行为**。

**（3）GOOSE 与 SV（本文的两个案例研究对象）**：

| 名称 | 全称 | 作用 | 通俗类比 |
|---|---|---|---|
| **GOOSE** | Generic Object Oriented Substation Event（通用面向对象变电站事件） | 传输**跳闸、联锁等快速控制命令**，要求毫秒级送达 | 站内的"紧急广播"——一声令下，所有相关设备立刻动作 |
| **SV** | Sampled Values（采样值） | 传输**电流电压的采样数据** | 站内的"实时直播"——把一次侧的电流电压波形连续播出来 |

论文明确指出这两者都是**组播消息（multicast messages）**——即一对多广播，**没有握手机制、没有加密、没有认证**（这是 IEC 61850 的早期设计特点）。**用网安的话说：这是一条完全开放的广播信道，任何人只要接入网络就能监听，也能伪造。** 这就是本文要解决的安全问题。

### 方法：LLM 驱动的网络安全框架

论文提出的框架是**基于大语言模型（Large Language Model, LLM）** 的，以 **ChatGPT** 为代表。框架有两个关键组成部分，其中第二个是论文强调的"首次"：

**组成部分一：通信系统的数据预处理（Data Pre-processing）**

**问题**：LLM 是处理自然语言的，它看不懂 IEC 61850 的二进制/结构化报文。**必须先把通信报文"翻译"成 LLM 能理解的形式。**

**这一步是整个流水线的关键适配层**，也是很多"LLM + 工控"论文容易忽略的地方。论文把它作为框架的第一个模块明确列出。

**组成部分二：人工在环训练（Human-in-the-Loop, HITL）——论文强调这是首次**

**做法**：在训练/提示过程中，**把人类推荐的安全指南（cybersecurity guidelines recommended by humans）作为输入纳入进来**。

**为什么这很重要？** 因为纯粹的"数据驱动"检测只能学到数据里出现过的模式。而**安全领域有大量先验知识**——比如"GOOSE 报文的 stNum 和 sqNum 字段不应该突然跳变""SV 采样值的变化率有物理上限"——这些是安全工程师的经验总结，**直接把这类规则以自然语言的形式喂给 LLM，是一种"知识注入"**。

> 论文用 "for the first time"（首次）强调这个设计，说明它认为**把人类安全指南与 LLM 结合**是这个工作的主要创新点。

**案例研究**：论文用 **GOOSE 和 SV 组播消息**作为案例，验证框架能否检测出这些通信中的异常。

### 实验：硬件在环测试床

论文使用 **硬件在环（Hardware-in-the-Loop, HIL）测试床**来**生成和提取 IEC 61850 通信数据集**。

**为什么用 HIL？** 因为真实的变电站不可能让你随便做攻击实验（那是关键基础设施）。HIL 的做法是：**把真实的保护/控制设备（硬件）接到一个实时仿真器上**，仿真器模拟电网的一次系统，硬件设备以为自己在真实电网里工作。**这样既真实、又安全、还可控。**

**结果**：论文对不同 LLM 做了**对比分析（comparative analysis）**，基于性能评价指标（performance evaluation metrics）来评估它们在检测异常数据上的表现。

> **摘要未给出具体数值**：没有给出检测准确率、误报率、具体比较了哪几个 LLM（除了标题里提到 ChatGPT）、也没有说明测试床的具体配置。这些都需要查原文。

## 关键公式（小白版）

这篇以**系统框架与实验对比**为主，摘要中没有给出需要展开的核心公式。它的技术路线是：

```
HIL 测试床生成 IEC 61850 通信数据（GOOSE / SV 报文）
  → 数据预处理：把报文转换成 LLM 可理解的形式
    → 人工在环（HITL）：注入人类安全专家的判断准则
      → LLM 推理：判断该报文/序列是否异常
        → 用性能指标横向比较不同 LLM
```

**理解这条路线，抓住两个要点就够了：**

1. **LLM 在这里不是"端到端的分类器"，而是"带知识的推理器"**。传统 IDS 是训练一个分类模型；这里是把报文"讲给"LLM 听，再结合人类给的规则让它判断。这个范式的优点是**可解释、易迭代**（改规则就行，不用重训）；缺点是**慢、贵、不确定**。
2. **数据预处理和 HITL 是这套方法能工作的两个前提**。没有预处理，LLM 读不懂协议；没有 HITL，LLM 缺少领域知识，容易产生幻觉式的误判。

## 用网安的话说（小电解读）

**这篇论文的核心命题，用网安的话说就是：能不能用 LLM 做一个"懂协议语义的 IDS"？**

**对照表**：

| 你熟悉的 | 这篇论文里的 |
|---|---|
| 基于规则的 IDS（Snort 规则） | 人工在环注入的安全指南（**本质上就是"自然语言写的规则"**） |
| 基于异常的 IDS（ML 模型） | LLM 对报文的语义理解 |
| 协议解析（协议逆向 / 报文解析） | 数据预处理模块 |
| 语义防火墙 | LLM 判断报文是否"语义异常" |
| 告警疲劳 / 误报 | LLM 幻觉导致的误判（**新问题**） |

**三个关键洞察：**

**第一，这篇论文其实是"用 LLM 重写规则引擎"。**

传统 IDS 的规则是"人写好的、结构化的"（`if GOOSE.stNum > prev + 1 then alert`）。这篇论文的思路是"**人用自然语言写规则，LLM 来执行**"。好处是规则可以写得很灵活（比如"如果采样值的跳变在物理上不可能，就报警"这种模糊表述），坏处是**执行不再确定**——同样的规则，LLM 两次可能给出不同答案。

> **"确定性"是安全系统的生命线**。一个 IDS 如果对同一个报文有时报警有时不报警，在工程上几乎不可用。这是 LLM 用于安全检测最大的软肋，也是你在选这个方向时必须正视的问题。

**第二，IEC 61850 的安全缺陷是本文的隐含前提。**

GOOSE 和 SV 是**组播、无认证、无加密**的。这意味着：

- 任何接入站内网络的人都能**监听**全部保护控制报文；
- 任何能发包的人都能**伪造**GOOSE 跳闸命令或篡改 SV 采样值。

**这就是 IEC 61850 早期设计的固有弱点**（后续的 IEC 62351 系列标准专门为它补充了安全机制）。**你如果做这个方向，一定要先搞清楚：目标是检测攻击，还是给协议本身加安全机制？** 后者是标准与工程问题，前者是检测问题。

**第三，"人工在环"这个设计，本质上是把安全工程师的经验做成了知识库。**

你熟悉的对应物是**威胁情报 + 检测规则库**。区别在于：传统规则库需要写成机器可执行的格式（正则、Sigma 规则）；HITL 允许用自然语言写。**这是"降低规则编写门槛"的一次尝试**，但代价是引入了 LLM 的不确定性。

**攻击面在哪**：IEC 61850 的组播通信链路。**注意：本文完全没有讨论"LLM 自身的安全问题"**——比如提示注入（见 075）。如果攻击者能在报文里植入一段"看起来像指令"的内容，LLM 会不会被带偏？**这是一个明确的研究空白，而且正好落在你实验室的方向上。**

**和 IT 场景的差异**：

- **同**：协议无认证 → 可伪造；组播 → 可监听。这些都是 IT 网络安全的经典问题。
- **异**：**实时性**。GOOSE 报文要求**毫秒级**送达并处理（跳闸命令不能等）。而 LLM 推理动辄几百毫秒到几秒。**把 LLM 放在在线检测环节，时间上根本来不及。** 论文的框架更适合**离线分析、事后取证、或者作为"慢速异常检测的第二道防线"**。这一点论文摘要没有讨论，但你在做选题时必须考虑。

**如果要迁移到你的研究**：

1. **提示注入攻击 LLM-based IDS**——把攻击载荷伪装成"安全指南"或"协议注释"，看能否让 LLM 忽略真正的异常。**这是"用 LLM 做安全"这个范式自带的攻击面，目前研究很少，且与 075 直接呼应。**
2. **LLM 检测的确定性与可复现性评估**——同一批报文多次推理，结果是否一致？不一致的比例有多高？这个"稳定性"指标在安全系统里比准确率更重要，但很少有人测。
3. **迁移到其他工控协议**——把框架搬到 Modbus/TCP、DNP3、OPC UA 上。数据预处理模块需要重写，但整体流水线可复用。**这是一个"工作量明确、结论清晰"的选题。**
4. **HITL 的知识注入方式对比**——把安全指南放在 system prompt、few-shot 示例、还是微调数据里，效果有何差异？这是一个偏工程的实验型题目。

## 局限性

- **摘要未给出任何具体数值**：没有检测准确率、误报率、延迟数据，也没有说明对比了哪几个 LLM（除 ChatGPT 外）。**"对比分析"这个结论无法从摘要层面验证。**
- **没有讨论 LLM 自身的攻击面**：论文把 LLM 当作可信的检测工具，完全没有考虑提示注入、越狱、数据投毒等针对 LLM 的攻击。**这是本文最大的空白，也是最有价值的后续方向。**
- **实时性问题完全没提**：GOOSE 报文的时间要求是毫秒级，而 LLM 推理是秒级。论文没有说明框架部署在哪个环节、能否满足时延要求。
- **确定性/可复现性问题没提**：LLM 输出的随机性对安全系统是致命问题，论文没有给出稳定性指标（比如重复推理的一致性）。
- **威胁模型不明确**：论文说"检测异常"，但没有说明攻击者能力假设（能否篡改报文？能否重放？能否注入新报文？）。没有威胁模型的检测论文，其结论的适用范围是模糊的。
- **数据集细节缺失**：HIL 测试床生成的数据集规模、包含哪些攻击类型、是否公开，摘要都没有说明。
- 论文发表时间较早（2023-11），用的是当时的 ChatGPT 等模型。**LLM 迭代极快，当时测出来的性能排名现在可能已经失效。**

## 原文摘要

> Cybersecurity breaches targeting electrical substations constitute a significant threat to the integrity of the power grid, necessitating comprehensive defense and mitigation strategies. Any anomaly in information and communication technology (ICT) should be detected for secure communications between devices in digital substations. This paper proposes large language models (LLM), e.g., ChatGPT, for the cybersecurity of IEC 61850-based digital substation communications. Multicast messages such as generic object oriented system event (GOOSE) and sampled value (SV) are used for case studies. The proposed LLM-based cybersecurity framework includes, for the first time, data pre-processing of communication systems and human-in-the-loop (HITL) training (considering the cybersecurity guidelines recommended by humans). The results show a comparative analysis of detected anomaly data carried out based on the performance evaluation metrics for different LLMs. A hardware-in-the-loop (HIL) testbed is used to generate and extract dataset of IEC 61850 communications.
