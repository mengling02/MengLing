## Day 75 · 09:00 —— IEC 61850 深度：SCL 配置与 MMS 通信

> **一句话**：**IEC 61850 不是"一个协议"，而是一套"用配置文件驱动的、面向对象的变电站建模体系"**。

### 一、IEC 61850 的定位

| 维度 | 说明 |
|---|---|
| **不是协议** | 是一套**标准体系**（含建模、配置、通信、测试） |
| **覆盖范围** | 变电站内的所有通信（保护、测控、计量） |
| **核心创新** | **面向对象建模 + 自描述配置** |
| **配套标准** | IEC 61850-1 ~ -10（多部分） |

### 二、信息模型：五层结构（核心）

```
Server（服务器）
  └─ Logical Device（逻辑设备，LD）
       └─ Logical Node（逻辑节点，LN）
            └─ Data Object（数据对象，DO）
                 └─ Data Attribute（数据属性，DA）
```

**具体例子**：

```
IED_1 (Server)
  └─ PROT（保护逻辑设备）
       └─ PDIS1（距离保护逻辑节点）
            └─ Pos（动作位置，数据对象）
                 └─ stVal（状态值，数据属性）← 真正读写的值
```

| 缩写 | 全称 | 含义 |
|---|---|---|
| **LN** | Logical Node | 功能单元（如距离保护 PDIS） |
| **DO** | Data Object | 数据对象（如"位置"） |
| **DA** | Data Attribute | 属性（如"状态值"、"品质"、"时标"） |

> 💡 **为什么要这样建模**？因为**自描述**：
> 任何 IED 都能用统一的 SCL 文件描述自己"有什么、能做什么"，
> 主站读一遍配置就知道全部功能 —— **不需要人工映射点表**。

### 三、SCL 配置文件家族

| 文件 | 全称 | 内容 | 谁生成 |
|---|---|---|---|
| **SSD** | System Specification Description | 单线图、拓扑 | 设计院 |
| **ICD** | IED Capability Description | IED 的能力描述 | **设备厂商** |
| **SCD** | Substation Configuration Description | **全站配置**（所有 IED） | 集成商 |
| **CID** | Configured IED Description | 下发到具体 IED 的配置 | 集成商 |

**配置流程**：
```
ICD（各厂商提供）
    ↓ 汇总
SCD（全站配置）
    ↓ 拆分
CID（下发到每个 IED）
```

### 四、MMS：IEC 61850 的"慢通道"

**MMS（Manufacturing Message Specification，制造报文规范）**：

| 维度 | 说明 |
|---|---|
| **用途** | 客户端-服务器通信（主站 ↔ IED） |
| **典型操作** | 读量测、**读/写保护定值**、报告 |
| **协议栈** | TCP/IP → ISO 会话/表示层 → MMS |
| **端口** | TCP 102 |
| **特点** | 可靠但慢（毫秒~秒级） |

> ⚠️ **关键点**：**MMS 支持"写"操作** —— 这意味着可以**远程修改保护定值**。
> 原版 IEC 61850 **没有认证机制**，任何能连上的人都能写。

### 五、安全含义（三个高危点）

| # | 问题 | 后果 |
|---|---|---|
| 1 | **MMS 可写且无认证** | 远程篡改保护定值 → 保护拒动/误动 |
| 2 | **SCL 文件是"配置即代码"** | 篡改 SCD → 全站配置错乱 |
| 3 | **信息模型可枚举** | 攻击者可"测绘"整个变电站结构 |

**攻击场景**：
```
攻击者接入站内网（或从主站侧渗透）
        ↓
① 用 MMS 浏览信息模型 → 枚举所有保护定值
        ↓
② 找到关键保护（如距离保护 II 段时限）
        ↓
③ MMS 写操作修改定值
        ↓
④ 故障时保护拒动 → 越级跳闸 → 大面积停电
```

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **"配置即代码"的攻击面** | SCL 文件 = 代码，篡改配置 = 攻击（类似供应链攻击） |
| **信息模型可枚举** | 攻击面测绘的"免费地图" |
| **写操作是高危原语** | 对比：Modbus 也能写，但 MMS 能写**保护定值** |
| **对接实验室方向** | **程序逆向**（解析 MMS/SCL）+ **入侵检测**（异常写操作） |

> 💡 **选题灵感**：
> 「**基于 SCL 基线比对的 IEC 61850 配置篡改检测**」
> - 思路：SCL 文件是**结构化**的 → 可以做**语义级 diff**
> - 攻击：修改保护定值、增删逻辑节点
> - 检测：与"经过审批的配置基线"比对 + 运行时的 MMS 写操作审计
> - 优势：**不需要机器学习**，工程上可直接落地（适合做实用型成果）

### 🔍 延伸思考

1. 如果攻击者篡改 SCD 文件后重新下发，站内会出现什么现象？
2. MMS 无认证的问题如何缓解？（提示：IEC 62351-4）

## Day 75 · 14:00 —— GOOSE 与 SV：变电站内的实时报文及其欺骗攻击

> **一句话**：**GOOSE 和 SV 是变电站的"快通道"，它们没有网络层、没有加密，却直接控制跳闸**——这是最危险的攻击面。

### 一、两种"快通道"报文

| 报文 | 传输内容 | 关键特性 |
|---|---|---|
| **GOOSE** | 状态量（跳闸、联锁、开关位置） | 多播、无确认、**毫秒级** |
| **SV** | 采样值（电流、电压瞬时值） | 多播、**高频（4 kHz）** |

> 💡 **对比 Day 75 上午的 MMS**：MMS 是"慢通道"（毫秒~秒），
> GOOSE/SV 是"快通道"（**微秒~毫秒**）。**实时性要求完全不同 → 设计完全不同。**

### 二、GOOSE 的技术特征

| 特征 | 说明 |
|---|---|
| **协议栈** | **直接跑在以太网二层**（无 IP、无 TCP！） |
| **通信模式** | 发布/订阅（Publisher/Subscriber） |
| **可靠性机制** | 心跳 + 变位重发 |
| **重发策略** | 变位后 2ms → 4ms → 8ms → ... 递增到稳定间隔 |
| **多播地址** | 固定的 MAC 多播地址范围 |

**为什么不用 IP？**
```
跳闸必须在 4 ms 内完成
        ↓
IP 层封装/解封装 + 路由查找 开销太大
        ↓
直接二层多播，最快
```

### 三、SV 的技术特征

| 特征 | 说明 |
|---|---|
| **采样率** | 80 点/周波 → **4 kHz**（50 Hz 系统） |
| **数据量** | 单个合并单元可达 **数十 Mbps** |
| **用途** | 保护算法的输入（差动、距离） |
| **标准** | IEC 61850-9-2 |

### 四、安全含义：为什么这是最危险的攻击面

| 设计缺陷 | 后果 |
|---|---|
| **无加密** | 报文可被**伪造** |
| **无认证** | 发送方可被**冒充** |
| **二层多播** | **接入即能发送**（不需要 IP 配置） |
| **无完整性校验** | 内容可被**篡改** |

> ⚠️ **一句话总结**：**在变电站内网里，只要能发包，就能发跳闸指令。**

### 五、四种典型攻击

| 攻击 | 手段 | 后果 | 隐蔽性 |
|---|---|---|---|
| **GOOSE 伪造** | 伪造跳闸报文 | **误跳闸** | 低（保护动作可见） |
| **GOOSE 重放** | 重放历史正常报文 | 状态混乱 | 中 |
| **GOOSE 洪泛** | 大量虚假报文 | **真跳闸送不到** | 中 |
| **SV 篡改** | 修改采样值 | 保护误判（拒动/误动） | **高** |

**SV 篡改最阴险**：
```
攻击者把某相电流采样值改小
        ↓
差动保护"看不到"故障电流
        ↓
保护拒动
        ↓
故障持续 → 设备损坏 → 扩大事故
```

### 六、防御手段

| 措施 | 原理 | 代价 |
|---|---|---|
| **IEC 62351-6** | 给 GOOSE/SV 加数字签名 | **引入延迟**（与实时性冲突） |
| **VLAN 隔离** | 把 GOOSE 流量隔离到专用 VLAN | 配置复杂 |
| **静态 MAC 绑定** | 交换机只允许特定 MAC 发送 | 运维负担 |
| **二层流量监测** | 检测异常 GOOSE | 需要专用工具 |

> 💡 **安全 vs 实时的根本矛盾**：
> GOOSE 要 4 ms 内送达，而签名验证需要时间。
> **这是工控安全的经典困境** —— 也是很好的研究题目。

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **最"物理"的攻击面** | 发个包就能跳闸，后果立竿见影 |
| **前提条件** | 需要物理接入或渗透进站内网（不是远程可达） |
| **检测难点** | 传统 IDS 看 IP 层，**看不见二层 GOOSE** |
| **对接实验室方向** | **入侵检测**（二层流量）+ **程序逆向**（GOOSE 协议栈实现分析） |

> 💡 **两个选题方向**：
> 1. 「**面向 GOOSE 的二层入侵检测：轻量级时序特征方法**」
>    —— 难点：4 ms 内要判完；优势：GOOSE 报文格式固定，特征清晰
> 2. 「**GOOSE 认证的延迟优化：如何兼顾 4 ms 与安全性**」
>    —— 难点：需要硬件加速；优势：工程价值极高

### 🔍 延伸思考

1. GOOSE 认证会引入延迟，如何权衡安全与实时性？（有没有"轻量级签名"方案？）
2. 如何检测 GOOSE 洪泛？洪泛和"正常变位风暴"如何区分？

### 参考

- IEC 61850-8-1（GOOSE 映射）
- IEC 61850-9-2（SV 采样值）
- IEC 62351-6（GOOSE/SV 安全）

## Day 76 · 09:00 —— Modbus/TCP 深度：为什么它天生不安全

> **一句话**：**Modbus 是 1979 年为串行总线设计的，搬到 TCP 上后没有任何安全机制**——它是工控安全的"活化石"。

### 一、历史背景（理解设计缺陷的根源）

```
1979 年 Modicon 公司为 PLC 通信设计
        ↓
原始形态：串行总线（RS-232 / RS-485）
    → 物理上隔离，只有一条线，谁能接上谁就能通信
    → "安全"靠物理隔离，不靠协议
        ↓
1990s~：封装到 TCP/IP（端口 502）
    → 物理隔离没了，但协议**一个字节都没改**
    → 缺陷被完整继承
```

> 💡 **关键认知**：Modbus 的不安全**不是设计失误**，而是**时代错位**——
> 它诞生在一个"物理隔离就是安全"的年代。

### 二、报文结构（简单到可以背下来）

```
┌──────────────────────────────────────────────────┐
│  MBAP 头（7 字节）                                │
├────────────┬────────────┬────────────┬───────────┤
│ 事务 ID    │ 协议 ID    │  长度      │  单元 ID  │
│ 2 字节     │ 2 字节     │  2 字节    │  1 字节   │
│（请求响应  │（恒为 0）  │（后续字节  │（从站地址）│
│  匹配）    │            │  数）      │           │
├────────────┴────────────┴────────────┴───────────┤
│  PDU                                              │
├────────────┬──────────────────────────────────────┤
│  功能码    │  数据                                 │
│  1 字节    │  N 字节                               │
└────────────┴──────────────────────────────────────┘
```

**整个协议只有两个关键字段：功能码 + 数据。没有认证、没有加密、没有会话。**

### 三、常用功能码（记住"读"和"写"的分界）

| 功能码 | 操作 | 对象 | 危险度 |
|---|---|---|---|
| **0x01** | 读 | 线圈（可读写开关量） | 低 |
| **0x02** | 读 | 离散输入（只读开关量） | 低 |
| **0x03** | 读 | 保持寄存器（可读写模拟量） | 低 |
| **0x04** | 读 | 输入寄存器（只读模拟量） | 低 |
| **0x05** | **写** | 单个线圈 | ⚠️ **高** |
| **0x06** | **写** | 单个寄存器 | ⚠️ **高** |
| **0x0F** | **写** | 多个线圈 | ⚠️ **高** |
| **0x10** | **写** | 多个寄存器 | ⚠️ **高** |

> 💡 **安全检测的核心思路**：**区分读操作和写操作**。
> 正常的 SCADA 采集几乎只有"读"，一旦出现"写"，就值得警惕。

### 四、设计缺陷清单

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **无认证** | 任何能连上 502 端口的人都能发指令 |
| 2 | **无加密** | 流量可嗅探、可篡改 |
| 3 | **无完整性校验** | 报文可伪造 |
| 4 | **长度字段校验宽松** | 可构造畸形包 |
| 5 | **无会话概念** | 无法追踪"谁做了什么" |
| 6 | **单元 ID 可广播（0）** | 一次影响所有从站 |

### 五、典型攻击手法

| 攻击 | 手段 | 常用工具 |
|---|---|---|
| **未授权读写** | 直接发功能码 | `modbus_cli`、`pymodbus` |
| **中间人篡改** | 改报文内容 | `ettercap`、`scapy` |
| **重放攻击** | 重放历史写指令 | `scapy` |
| **畸形包 DoS** | 长度字段异常 | 自写脚本 |
| **资产测绘** | 遍历单元 ID / 功能码 | `nmap` + modbus 脚本 |

**一个最小攻击示例（scapy 思路）**：
```python
# 写单个线圈（功能码 0x05）
# 把地址 0x0001 的线圈置为 ON
payload = bytes([
    0x00, 0x01,   # 事务 ID
    0x00, 0x00,   # 协议 ID
    0x00, 0x06,   # 长度
    0x01,         # 单元 ID
    0x05,         # 功能码：写单个线圈
    0x00, 0x01,   # 线圈地址
    0xFF, 0x00,   # 值：ON
])
# 直接 TCP 发送到 502 端口 → 现场设备动作
```

### 六、绕过与防护

| 绕过思路 | 说明 |
|---|---|
| **范围校验缺失** | 部分设备只校验功能码，不校验地址范围 |
| **单元 ID 广播** | 用 ID=0 一次影响所有从站 |
| **异常响应区分** | 通过错误码差异探测设备型号 |

| 防护措施 | 原理 | 局限 |
|---|---|---|
| **深度包检测（DPI）** | 解析 Modbus，检查功能码/地址 | 需知道正常行为基线 |
| **白名单** | 只允许特定"功能码 + 地址范围"组合 | 配置维护成本高 |
| **IEC 62351** | 标准安全扩展 | 部署率低 |
| **网络分段** | 物理/逻辑隔离 | 内部人仍可绕过 |

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **最容易入门的工控协议** | 报文简单，适合作为**第一个实验对象** |
| **白名单检测是工业界主流** | 但"如何自动生成白名单"是研究问题 |
| **对接实验室方向** | **入侵检测**（协议异常检测）+ **程序逆向**（协议实现分析） |

> 💡 **一个非常适合上手的选题**：
> 「**基于语义白名单的 Modbus 异常检测：自动学习"正常行为画像"**」
> - 传统白名单靠人工配置 → 工作量大、易漏
> - 你的方法：用**无监督学习**从历史流量自动学出"每个设备正常会做什么"
> - 优势：**数据容易造**（用 pymodbus 模拟即可）、**实验周期短**、**易出成果**
> - 这个方向特别适合作为你的**第一篇论文**（低风险、可快速完成）

### 🔍 延伸思考

1. 为什么 Modbus 至今还在大量使用？（提示：兼容性、简单性、替换成本）
2. 基于白名单的检测能否被绕过？攻击者如何"伪装成正常操作"？

## Day 76 · 14:00 —— DNP3 安全认证与绕过

> **一句话**：**DNP3 是电力远动的主力协议，它有安全扩展（SAv5），但部署率低、且仍有绕过空间**。

### 一、DNP3 的定位

| 维度 | 说明 |
|---|---|
| **应用地区** | **北美**电力系统主流远动协议 |
| **功能** | 遥测、遥信、遥控、遥调（完整四遥） |
| **复杂度** | 比 Modbus 复杂得多（对象模型、时标、事件缓冲） |
| **优势** | 支持**事件缓冲**（断线后可补传）、时间戳精度高 |

### 二、协议层次结构

```
┌─────────────────────────────┐
│  应用层（APDU）              │  ← 对象模型、功能码
├─────────────────────────────┤
│  传输层（伪传输层）           │  ← 分片重组
├─────────────────────────────┤
│  数据链路层                  │  ← 帧、CRC、地址
├─────────────────────────────┤
│  物理层（串行 / TCP）        │
└─────────────────────────────┘
```

### 三、链路层帧结构

| 字段 | 长度 | 说明 |
|---|---|---|
| **起始字节** | 2 B | 固定 `0x05 0x64` |
| **长度** | 1 B | 帧长 |
| **控制** | 1 B | 方向 + 功能 |
| **目的地址** | 2 B | 从站地址 |
| **源地址** | 2 B | 主站地址 |
| **CRC** | 2 B | 校验（**防误码，不防篡改**） |
| 用户数据 | N B | 应用层数据 |
| CRC | 2 B | 数据部分校验 |

> ⚠️ **注意**：CRC 只能防**传输误码**，攻击者可以**重新计算 CRC** —— 它**不是安全机制**。

### 四、应用层对象模型

DNP3 用"对象组（Group）+ 变体（Variation）"表示数据：

| 对象组 | 内容 | 对应四遥 |
|---|---|---|
| **Group 1** | 二进制输入 | 遥信 |
| **Group 10** | 二进制输出 | **遥控** |
| **Group 30** | 模拟量输入 | 遥测 |
| **Group 40** | 模拟量输出 | **遥调** |
| Group 50 | 时间 | — |

### 五、DNP3 安全认证（SAv5）

| 特性 | 说明 |
|---|---|
| **认证机制** | **挑战-应答**（Challenge-Response）+ HMAC |
| **防重放** | 序列号 + 时间窗口 |
| **保护范围** | **关键操作**（遥控、遥调）必须认证 |
| **算法** | HMAC-SHA-256（SAv5） |
| **密钥管理** | 预共享密钥（PSK）或证书 |

**认证流程**：
```
主站 → 从站：我要执行遥控（无认证）
从站 → 主站：给你一个挑战码（Challenge）
主站 → 从站：HMAC(挑战码, 密钥)
从站：验证 HMAC → 通过则执行
```

### 六、SAv5 的五个局限

| # | 局限 | 说明 |
|---|---|---|
| 1 | **部署率低** | 大量老旧设备不支持 SA |
| 2 | **只保护关键操作** | 遥测读取可能不认证 → 可被用于**测绘** |
| 3 | **密钥管理困难** | 现场运维不便，常被简化 |
| 4 | **认证前可洪泛** | DoS 不需要通过认证 |
| 5 | **降级风险** | 可协商回退到无认证模式 |

### 七、绕过思路

| 绕过手法 | 原理 | 难度 |
|---|---|---|
| **降级攻击** | 强制协商回退到无认证模式 | 中 |
| **密钥泄露** | 从现场配置文件提取 PSK | 低（物理接入） |
| **认证前洪泛** | 认证前就能耗尽资源 | 低 |
| **利用未认证的读** | 通过遥测读取测绘系统 | 低 |
| **重放 + 时间窗口** | 若时间窗口宽松则可重放 | 中 |

> 💡 **降级攻击是通用范式**：
> 任何"可选安全机制"都可能被降级 —— SSL 有 SSL Strip，DNP3 有 SA 降级。
> **这是"安全机制的可协商性"带来的固有风险。**

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **DNP3 SA 是"工控协议安全"的典型样本** | 有安全机制，但部署和实现有问题 |
| **降级攻击是通用思路** | 可迁移到其他协议（IEC 61850、OPC UA） |
| **"协议安全机制有效性评估"是研究空白** | 很少有人系统评估 SA 的实际防护效果 |
| **对接实验室方向** | **入侵检测**（认证失败模式）+ **程序逆向**（SA 实现分析） |

> 💡 **选题灵感**：
> 「**DNP3 安全认证的降级攻击与检测**」
> - 攻击：诱导主从站协商到无认证模式，然后执行未授权遥控
> - 检测：监控**协商过程**（安全等级变更本身就是强信号）
> - 新意：现有研究关注"认证强度"，很少关注"**认证协商过程**"的安全
> - 优势：协议规范公开，可以用开源实现（如 `opendnp3`）搭建实验环境

### 🔍 延伸思考

1. **降级攻击**如何防御？（提示：强制最低安全等级 + 变更告警）
2. SAv5 的密钥管理在实践中如何做？现场设备众多时怎么办？

## Day 77 · 09:00 —— IEC 60870-5-104：调度主站与变电站之间的语言

> **一句话**：**104 规约是中国电网调度自动化的主力协议**——它比 Modbus 规范得多，但同样**没有认证**。

### 一、104 的定位

| 维度 | 说明 |
|---|---|
| **应用地区** | **中国**电网调度（主流） |
| **来源** | IEC 60870-5-101 的 **TCP/IP 版本** |
| **关系** | 101 = 串行版；**104 = 网络版**（端口 **2404**） |
| **用途** | 调度主站 ↔ 变电站（远动通信） |

### 二、协议结构：APCI + ASDU

```
┌──────────────────────────────────────────┐
│  APCI（应用规约控制信息，6 字节）          │
├────────┬────────┬────────────────────────┤
│ 启动   │ 长度   │  控制域（4 字节）       │
│ 0x68   │ 1 字节 │  I 帧 / S 帧 / U 帧     │
├────────┴────────┴────────────────────────┤
│  ASDU（应用服务数据单元）                  │
│  ← 真正的业务数据                          │
└──────────────────────────────────────────┘
```

### 三、三种帧类型

| 帧型 | 名称 | 用途 | 是否带数据 |
|---|---|---|---|
| **I 帧** | 信息传输格式 | 携带 ASDU 业务数据 | ✅ 是 |
| **S 帧** | 监视格式 | 确认收到 | ❌ 否 |
| **U 帧** | 无编号格式 | 链路控制（启动/停止/测试） | ❌ 否 |

### 四、ASDU 结构（报文的核心）

| 字段 | 说明 |
|---|---|
| **类型标识（TI）** | 报文类型（如 1 = 单点遥信） |
| **可变结构限定词（VSQ）** | 是否连续、信息对象数量 |
| **传送原因（COT）** | 周期 / 突发 / 命令 / 初始化 |
| **公共地址** | 站地址 |
| **信息对象地址（IOA）** | 具体测点编号 |
| **信息元素** | 值 + 品质 + 时标 |

### 五、常用类型标识（TI）

| TI | 内容 | 对应 |
|---|---|---|
| **1** | 单点信息 | 遥信 |
| **3** | 双点信息 | 遥信（带中间态） |
| **9** | 归一化测量值 | 遥测 |
| **13** | 浮点测量值 | 遥测 |
| **45** | 单点命令 | ⚠️ **遥控** |
| **100** | 总召唤 | 全量数据请求 |
| **103** | 时钟同步 | 对时 |

> 💡 **安全检测的关键**：**TI = 45（遥控）是最高危的操作**。
> 正常采集流量里几乎不会出现遥控命令 —— 一旦出现就值得告警。

### 六、安全缺陷清单

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **无认证** | 可发遥控命令 |
| 2 | **无加密** | 可嗅探、可篡改 |
| 3 | **无完整性校验** | 可伪造 |
| 4 | **总召唤可滥用** | 反复总召唤 → DoS |
| 5 | **时钟同步无保护** | 篡改时标 → 事件顺序混乱 |
| 6 | **无会话审计** | 无法追溯操作者 |

### 七、典型攻击手法

| 攻击 | 手段 | 后果 |
|---|---|---|
| **未授权遥控** | 直接发 TI=45 | 开关误动作 |
| **遥测篡改** | 改 TI=9/13 的值 | 调度员误判 |
| **总召唤洪泛** | 反复发 TI=100 | 通道拥塞、CPU 满载 |
| **时钟欺骗** | 篡改 TI=103 | 事件时标错乱，事后分析失效 |
| **资产测绘** | 遍历公共地址 + IOA | 完整拓扑还原 |

> ⚠️ **时钟同步攻击特别值得注意**：
> 电力系统的**事件顺序记录（SOE）**依赖精确时标。
> 攻击者篡改时钟 → 故障录波时序错乱 → **事后调查无法还原真实过程**。
> 这是一种"**抹除证据**"的攻击，比直接破坏更隐蔽。

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **研究价值高** | 104 是中国电网最常用的远动协议，但安全研究**远少于 Modbus/DNP3** |
| **开源实现丰富** | `lib60870`、`FreyrSCADA` 等，便于搭建实验环境 |
| **检测思路清晰** | 白名单（TI + IOA 范围）+ 语义校验 |
| **对接实验室方向** | **入侵检测**（协议语义）+ **程序逆向**（104 协议栈分析） |

> 💡 **一个很适合上手的选题**：
> 「**基于 ASDU 语义的 104 规约异常检测：从"报文合法"到"业务合理"**」
> - 传统 DPI 只检查"报文格式对不对"
> - 你的方法检查"**业务逻辑合不合理**"：
>   - 遥控命令是否在允许的时间窗内？（如夜间无人操作时段的遥控可疑）
>   - 遥测值变化率是否物理合理？（不可能 1 秒内从 0 跳到满载）
>   - 总召唤频率是否异常？
> - 优势：**语义特征可解释**（审稿人喜欢）、**数据易造**（用 lib60870 模拟）

### 🔍 延伸思考

1. 104 的"总召唤"机制能否被滥用做 DoS？如何区分"正常总召唤"和"攻击性洪泛"？
2. 时钟同步攻击对**故障录波**有什么影响？为什么说这是"抹除证据"？

## Day 77 · 14:00 —— OPC UA 安全模型：工控领域少有的"原生安全"设计

> **一句话**：**OPC UA 是工控协议里少见的"设计时就考虑安全"的协议**——但复杂的配置反而带来了新的风险。

### 一、OPC UA 的定位

| 维度 | 说明 |
|---|---|
| **来源** | 从 OPC Classic（依赖 Windows DCOM）演进而来 |
| **架构** | 跨平台、**面向服务（SOA）** |
| **用途** | MES / SCADA ↔ 设备、系统间集成 |
| **端口** | TCP **4840** |
| **特点** | **原生安全设计**（不是后补的） |

### 二、安全模型（核心优势）

| 机制 | 说明 |
|---|---|
| **认证** | X.509 证书 / 用户名密码 |
| **加密** | AES、ChaCha20 |
| **完整性** | 数字签名 |
| **授权** | 用户角色 + 细粒度权限 |
| **审计** | 安全审计日志 |
| **不可否认** | 数字签名支持 |

### 三、安全模式（Security Mode）

| 模式 | 含义 | 安全性 |
|---|---|---|
| **None** | 无安全 | ❌ **危险**（等价于 Modbus） |
| **Sign** | 只签名（不加密） | ⚠️ 防篡改但不防窃听 |
| **SignAndEncrypt** | 签名 + 加密 | ✅ **推荐** |

### 四、安全策略（Security Policy）

| 策略 | 强度 | 说明 |
|---|---|---|
| `None` | ❌ | 无保护 |
| `Basic128Rsa15` | ⚠️ 已废弃 | 早期默认 |
| `Basic256` | ⚠️ 已废弃 | SHA-1 |
| **`Basic256Sha256`** | ✅ | 当前推荐下限 |
| `Aes128_Sha256_RsaOaep` | ✅ | 较新 |
| `Aes256_Sha256_RsaPss` | ✅ **最强** | 推荐 |

> ⚠️ **废弃策略仍被广泛使用** —— 因为老旧设备只支持它们。

### 五、证书管理：最容易出问题的地方

```
① 应用实例证书（Application Instance Certificate）
   → 每个 OPC UA 应用必须有唯一证书
        ↓
② 信任列表（Trust List）
   → 手动或自动把对方证书加入信任列表
        ↓
③ 证书吊销（CRL）
   → 证书泄露后如何吊销？
        ↓
④ 首次信任问题（GTOFU - Trust On First Use）
   → 第一次连接时如何确认对方身份？
```

> 💡 **GTOFU 是经典难题**：第一次连接时你**无法验证**对方证书是否合法，
> 只能"先信任"。如果攻击者在第一次连接时就冒充 → **中间人攻击成功**。

### 六、常见配置错误（攻击者的真正入口）

| # | 错误配置 | 后果 |
|---|---|---|
| 1 | 使用 **None 模式** | 完全不安全 |
| 2 | 信任列表**过宽** | 任意证书可连 |
| 3 | 证书**不过期** | 泄露后长期有效 |
| 4 | 开启**匿名登录** | 无需认证即可访问 |
| 5 | 端口**暴露公网** | 直接可达 |
| 6 | 使用**废弃安全策略** | 可被破解 |

> ⚠️ **一个反直觉的结论**：
> **"有安全机制"的协议，可能比"没有安全机制"的协议更危险**。
> 因为 Modbus 大家都知道不安全，会做隔离；
> 而 OPC UA 有安全机制，运维人员**以为配好就安全了** ——
> 结果用了 None 模式或过宽的信任列表，反而更危险。

### 七、典型攻击手法

| 攻击 | 手段 | 前提 |
|---|---|---|
| **降级到 None** | 中间人修改协商 | 能劫持流量 |
| **证书伪造** | 利用过宽信任列表 | 配置错误 |
| **匿名访问** | 利用匿名登录配置 | 配置错误 |
| **信息模型枚举** | 读取地址空间 | 未授权访问 |
| **DoS** | 畸形报文 | 任意 |

### 八、OPC UA vs 传统工控协议（对比总结）

| 维度 | Modbus / DNP3 / 104 | **OPC UA** |
|---|---|---|
| **安全设计** | 后补（甚至没有） | ✅ **原生** |
| **认证** | 无 / 可选 | ✅ **内建** |
| **加密** | 无 | ✅ **内建** |
| **协议复杂度** | 低 | **高** |
| **配置风险** | 低（因为没得配） | ⚠️ **高（配错就完）** |
| **主要威胁** | 协议缺陷 | **配置错误** |

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **"配置安全"是新的研究点** | 有安全机制 ≠ 安全（配置错误是主因） |
| **自动化配置审计有价值** | 可做工具类成果，工程落地性强 |
| **对接实验室方向** | **程序逆向**（OPC UA 协议栈）+ **入侵检测**（异常访问模式） |

> 💡 **一个工程价值很高的选题**：
> 「**OPC UA 部署配置安全审计：自动识别不安全配置**」
> - 检查项：安全模式、安全策略、信任列表宽度、匿名访问、证书有效期
> - 方法：主动探测（作为客户端连接并协商）+ 被动流量分析
> - 优势：**结果直观**（可给出风险评分）、**易于落地**、**适合做工程型论文**
> - 这条路线特别契合实验室的「**工业AI与智能体**」——可以做成一个**审计智能体**

## Day 78 · 09:00 —— 工控流量解析实战：从 pcap 到语义

> **一句话**：**拿到一个 pcap，你要能回答三个问题：谁在跟谁说话、说了什么、有没有异常**。

### 一、标准分析流程（五步）

```
① 流量概览 → 有哪些 IP？通信关系是什么？
        ↓
② 协议识别 → 用的是什么协议？（Modbus / 104 / GOOSE / 私有）
        ↓
③ 会话还原 → 把 TCP 流拼成完整的请求-响应
        ↓
④ 语义解析 → 每个字段什么意思？（功能码、地址、值）
        ↓
⑤ 异常发现 → 哪里不符合"正常行为"？
```

### 二、工具链

| 工具 | 类型 | 用途 |
|---|---|---|
| **Wireshark** | GUI | 通用分析 + 工控协议解析 |
| **tshark** | CLI | 命令行解析（可脚本化） |
| **Zeek** | 框架 | 网络监控 + 结构化日志 |
| **tcpdump** | CLI | 抓包 |
| **NetworkMiner** | GUI | 资产提取、文件还原 |
| **GRASSMARLIN** | GUI | **工控拓扑自动测绘**（NSA 开源） |

> 💡 **建议组合**：
> **tcpdump 抓包 → tshark 批量解析 → Python 做统计分析**。
> 这套组合最适合做实验（可复现、可自动化）。

### 三、Wireshark 的工控协议支持

Wireshark **内置**支持主流工控协议（不需要插件）：

| 协议 | 显示过滤器 | 说明 |
|---|---|---|
| Modbus/TCP | `modbus` | 自动解析功能码 |
| DNP3 | `dnp3` | 解析对象组 |

### 四、解析实战 ①：Modbus

```
过滤器：modbus
```

| 看什么 | 在哪看 | 异常信号 |
|---|---|---|
| **功能码** | 报文详情 | 出现 0x05/0x06/0x0F/0x10（写） |
| **地址** | 报文详情 | 超范围、非连续 |
| **值** | 报文详情 | 突变、越界 |
| **通信关系** | Statistics → Conversations | 出现新的主站 IP |

**快速统计**：`Statistics → Protocol Hierarchy` 看各协议占比。

### 五、解析实战 ②：IEC 104

```
过滤器：iec60870_104
```

| 关键字段 | 含义 | 异常信号 |
|---|---|---|
| **类型标识（TI）** | 报文类型 | **出现 TI=45（遥控）** |
| **传送原因（COT）** | 为什么发 | 异常的 COT |
| **信息对象地址（IOA）** | 哪个测点 | 超范围、遍历式访问 |
| **公共地址** | 哪个站 | 出现未知站地址 |

### 六、异常发现的五个维度（核心框架）

| 维度 | 正常表现 | 异常表现 |
|---|---|---|
| **① 通信关系** | 固定的主从对 | 出现**新设备**、新连接 |
| **② 操作类型** | 只有读（采集） | 出现**写 / 遥控 / 参数修改** |
| **③ 通信频率** | 稳定周期 | **突发洪泛** 或异常静默 |
| **④ 数值特征** | 物理合理、变化平滑 | **越界、跳变、长时间不变** |
| **⑤ 时间特征** | 规律 | **异常时刻**（深夜、故障前后） |

> 💡 **这五个维度就是特征工程的骨架** —— 你的检测器特征可以从这五个方向设计。

### 七、从解析到检测（完整链路）

```
pcap 文件
    ↓ tshark 提取字段
结构化数据（时间, 源IP, 目的IP, 功能码, 地址, 值）
    ↓ 特征工程
特征向量（五维度的统计量）
    ↓ 建立基线（正常流量）
    ↓ 检测偏离
告警
```

| 要点 | 说明 |
|---|---|

| **这是你实验的核心技能** | 建议**至少完整解析一个真实 pcap** |
| **对接实验室方向** | **入侵检测**（核心）+ **程序逆向**（私有协议解析） |

> 💡 **实操建议**：
> 去抓一个**真实的工控流量 pcap**（或用 `pymodbus` + `lib60870` 自己造），
> 然后用 tshark 导出成 CSV，用 pandas 分析。
> **这一步做过一遍，你对工控协议的理解会从"知道"变成"会用"。**

## Day 78 · 14:00 —— 协议模糊测试（Fuzzing）方法论

> **一句话**：**Fuzzing 是自动"乱试"协议输入来触发漏洞**——它是工控漏洞挖掘的主力方法。

### 一、Fuzzing 的基本思想

```
自动生成大量（半）畸形输入
        ↓
发送给目标（协议栈 / 设备）
        ↓
观察是否崩溃 / 异常 / 超时
        ↓
崩溃 = 潜在漏洞
```

**为什么有效？** 因为**人类写代码必然会漏掉边界情况**，而 Fuzzing 可以穷举这些边界。

### 二、三种 Fuzzing 类型

| 类型 | 是否知道内部 | 优点 | 缺点 | 代表工具 |
|---|---|---|---|---|
| **黑盒** | ❌ 只知输入输出 | 简单、无需源码 | 覆盖率低 | SPIKE |
| **白盒** | ✅ 有源码 | 覆盖率高 | 需要源码 | 符号执行工具 |
| **灰盒** ⭐ | ⚠️ 有反馈信号 | **平衡** | 需要插桩 | **AFL++** |

> 💡 **灰盒是当前主流**：通过"覆盖率反馈"引导变异方向 ——
> 能触发新代码路径的输入会被保留并继续变异。

### 三、协议 Fuzzing 的五个特殊挑战

| # | 挑战 | 说明 |
|---|---|---|
| 1 | **状态机** | 协议有状态，不能乱序发送（要先连接、先认证） |
| 2 | **校验和** | CRC/校验和必须正确，否则**到不了深层逻辑** |
| 3 | **长度字段** | 长度必须自洽，否则解析器直接丢弃 |
| 4 | **认证** | 很多操作需要先通过认证 |
| 5 | **实时性** | 工控设备**不能随便搞崩**（会影响生产） |

> ⚠️ **第 2 条最关键**：**如果你的畸形包连校验和都过不了，测试的是"校验和逻辑"而不是"业务逻辑"**。
> 所以协议 Fuzzing 必须**先实现正确的校验和计算**。

### 四、常用工具

| 工具 | 类型 | 特点 |
|---|---|---|
| **AFL++** | 通用灰盒 | 覆盖率引导，最流行 |
| **BooFuzz** | 协议专用 | Python 编写，**支持状态机** |
| **Peach Fuzzer** | 协议专用 | 基于数据模型（Pit 文件） |
| **SPIKE** | 协议专用 | 块结构描述 |
| **Sulley** | 协议专用 | 老牌框架 |

**推荐**：**BooFuzz** —— Python 编写，容易上手，支持协议状态机，社区活跃。

### 五、针对工控协议的 Fuzzing 思路

```
第 1 步：用协议规范构造"合法模板"
    → Modbus 写单个寄存器：
      [事务ID][协议ID][长度][单元ID][0x06][地址][值]

第 2 步：识别"关键字段"
    → 长度、功能码、地址、值

第 3 步：定向变异（保持结构，只改关键字段）
    → 长度字段与数据不匹配
    → 功能码越界（0x00, 0x7F, 0xFF）
    → 地址超范围（0xFFFF）
    → 值长度异常

第 4 步：维护校验和正确性
    → 重新计算 CRC

第 5 步：维护协议状态
    → 先连接、先认证，再发送畸形包
```

### 六、Modbus Fuzzing 具体示例

| 字段 | 合法值 | 变异策略 |
|---|---|---|
| 事务 ID | 任意 2 B | 固定/随机 |
| 协议 ID | `0x0000` | 改为非 0（**违规**） |
| **长度** | 与数据匹配 | **故意不匹配**（过大/过小） |
| 单元 ID | 1 ~ 247 | 0（广播）、248~255 |
| **功能码** | 01~10 | **0x00、0x7F、0xFF、未定义码** |
| **地址** | 0 ~ 0xFFFF | **0xFFFF、超范围** |
| 值 | 按类型 | **长度异常、极值** |

### 七、Fuzzing 的局限与伦理

| 局限 / 风险 | 说明 |
|---|---|
| **设备可能崩溃** | 可能影响生产 → **必须用测试环境** |
| 需要测试环境 | 成本高（真机 or 仿真） |
| **只能发现"崩溃类"漏洞** | 逻辑漏洞（如认证绕过）Fuzzing 找不到 |
| 覆盖率难保证 | 深层逻辑可能测不到 |
| **法律与伦理** | 未经授权测试他人设备**违法** |

> ⚠️ **务必注意**：**只在自有或明确授权的测试环境做 Fuzzing**。
> 对生产系统做 Fuzzing 可能造成停电事故 —— 这是**刑事风险**。

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **漏洞挖掘的核心技能** | 直接对接实验室「**程序逆向**」方向 |
| **工控协议 Fuzzing 是活跃研究领域** | 每年都有新漏洞（ICS-CERT 公告） |
| **AI + Fuzzing 是热点** | 用机器学习**引导变异**方向，提高效率 |
| **对接实验室方向** | **程序逆向**（漏洞挖掘）+ **工业AI**（智能变异） |

> 💡 **一个前沿选题**：
> 「**基于强化学习的工控协议模糊测试：用覆盖率反馈引导变异策略**」
> - 传统 AFL 用随机变异 + 覆盖率反馈
> - 你的方法：用 RL 学习"**哪些字段值得变异**"
> - 优势：**创新点明确**、**可量化对比**（覆盖率、崩溃数）、**工具链成熟**
> - 难点：需要搭建设备仿真环境（可用 `conpot` 蜜罐或软 PLC）

### 🔍 延伸思考

1. 如何在不影响生产的前提下 Fuzz 工控设备？（提示：数字孪生 / 硬件在环）
2. AI 如何改进 Fuzzing 的效率？为什么"覆盖率反馈"还不够？

## Day 79 · 09:00 —— 固件提取与逆向工具链

> **一句话**：**固件是工控设备的"灵魂"**——提取并逆向它，是找漏洞的必经之路。

### 一、为什么必须关注固件

| 原因 | 说明 |
|---|---|
| **核心逻辑在固件里** | 协议实现、业务逻辑、认证机制全在固件 |
| **常见硬编码凭据** | 厂商为了"方便运维"留下固定密码 |
| **可能有后门** | 调试接口、隐藏账户 |
| **更新机制可被利用** | 签名校验缺失 → 刷入恶意固件 |
| **逆向是漏洞挖掘的前提** | 不懂固件，只能黑盒瞎试 |

### 二、固件获取的五种途径

| 途径 | 难度 | 说明 |
|---|---|---|
| **厂商官网下载** | ⭐ | 最简单，升级包直接下载 |
| **网络升级流量** | ⭐⭐ | 抓取设备升级时的流量 |
| **泄露/共享** | ⭐ | 论坛、研究社区 |
| **设备提取（UART）** | ⭐⭐⭐ | 串口连上，常能拿到 shell |
| **设备提取（JTAG/SPI）** | ⭐⭐⭐⭐ | 需要硬件工具 |

### 三、硬件提取的四种接口

| 接口 | 全称 | 能力 | 难度 |
|---|---|---|---|
| **UART** | 通用异步收发器 | 串口终端，常有 shell | 低（需 USB-TTL） |
| **JTAG** | 联合测试行动组 | **读写内存、单步调试** | 中高 |
| **SPI Flash** | 串行外设接口闪存 | **直接读整片固件** | 中（需编程器） |
| **SWD** | 串行线调试 | ARM 芯片调试 | 中高 |

> 💡 **实操顺序建议**：**先试 UART**（最容易，找到 TX/RX/GND 三根线即可）。
> 很多设备的 UART 会直接给出 root shell 或 U-Boot 提示符。

### 四、固件解析：binwalk 标准流程

```bash
# ① 识别固件里有什么（文件系统、压缩包、内核）
binwalk firmware.bin

# ② 自动提取所有可识别的内容
binwalk -e firmware.bin

# ③ 如果识别到 SquashFS，手动解压
unsquashfs -d ./rootfs squashfs-root.sqsh

# ④ 如果被加密/混淆，需要先找解密逻辑
```

**常见文件系统**：

| 文件系统 | 特点 | 解压工具 |
|---|---|---|
| **SquashFS** | 只读压缩，最常见 | `unsquashfs` |
| **CramFS** | 更老的只读压缩 | `cramfsck` |
| **JFFS2** | 可读写，日志型 | `jefferson` |
| **UBIFS** | NAND 闪存常用 | `ubireader` |
| **ext2/3/4** | 标准 Linux | `mount` |

### 五、逆向工具对比

| 工具 | 类型 | 优点 | 缺点 |
|---|---|---|---|
| **IDA Pro** | 商业 | 最强，反编译好 | **贵** |
| **Ghidra** | 免费（NSA） | **免费、反编译强** | 界面略慢 |
| **radare2 / rizin** | 开源 | 脚本化强、轻量 | 学习曲线陡 |
| **Binary Ninja** | 商业 | 中间语言清晰 | 贵 |
| **angr** | 开源 | **符号执行**、自动化 | 复杂、慢 |

> 💡 **推荐组合**：**Ghidra（主力）+ radare2（脚本批量）+ angr（特定自动化）**。
> 全免费，够用。

### 六、固件分析的六个重点

| # | 分析点 | 找什么 | 危害 |
|---|---|---|---|
| 1 | **硬编码凭据** | 密码、密钥、token | 高 |
| 2 | **后门账户** | 隐藏的 root 用户 | 高 |
| 3 | **命令注入** | `system()` 拼接用户输入 | 高 |
| 4 | **缓冲区溢出** | `strcpy`/`sprintf` 无边界检查 | 高 |
| 5 | **加密密钥** | 硬编码的对称密钥 | 高 |
| 6 | **更新机制** | 签名校验是否缺失 | **极高** |

### 七、自动化工具（提高效率的关键）

| 工具 | 用途 | 说明 |
|---|---|---|
| **Firmwalker** | 快速扫描敏感文件 | 找 `/etc/passwd`、私钥、URL |

> ```

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **固件逆向 = 程序逆向方向的核心技能** | 直接对接实验室方向 |
| **工控固件漏洞是 ICS-CERT 公告的主要来源** | 有实际影响力 |
| **供应链视角** | 同一固件被多个厂商使用 → 一个漏洞影响一片 |
| **对接实验室方向** | **程序逆向**（核心）+ **固件安全** |

> 💡 **一个容易出成果的方向**：
> 「**电力设备固件的自动化安全扫描：从 binwalk 到漏洞定位**」
> - 痛点：现有工具（Firmwalker 等）只做**浅层扫描**，误报多
> - 你的方法：结合**危险函数可达性分析**（不是"用了 strcpy"就有洞，要看**输入是否可控**）
> - 优势：**结果可量化**（真漏洞数 vs 误报数）、**工程价值高**
> - 这条路线可以做成工具型论文，也可以做成"AI 辅助漏洞定位"

## Day 79 · 14:00 —— 电力嵌入式设备漏洞挖掘实战思路

> **一句话**：**把逆向技能用到电力设备上，你能找到 ICS-CERT 级别的漏洞**。

### 一、电力设备的攻击价值排序

| 设备 | 漏洞后果 | 攻击价值 |
|---|---|---|
| **保护装置（IED）** | 拒动/误动 → **大停电** | ★★★★★ |
| **RTU / DTU** | 数据篡改、遥控劫持 | ★★★★ |
| **智能电表** | 计量欺诈、**大规模控制** | ★★★★ |
| **站内网关** | 内网跳板 | ★★★ |
| **逆变器** | 影响电网稳定 | ★★★★ |
| **合并单元** | SV 采样值伪造 | ★★★★★ |

### 二、漏洞挖掘的五个切入点

| # | 切入点 | 为什么容易出洞 |
|---|---|---|
| 1 | **协议解析模块** | 输入完全可控，边界检查常缺失 |
| 2 | **Web 管理界面** | 常见注入、认证绕过 |
| 3 | **认证模块** | 硬编码、逻辑缺陷 |
| 4 | **固件更新模块** | 签名校验常被省略 |
| 5 | **通信模块** | 内存破坏、状态机缺陷 |

### 三、六类典型漏洞

| 类型 | 说明 | 危害 | 挖掘方法 |
|---|---|---|---|
| **硬编码凭据** | 固件里有固定密码 | 高 | 字符串搜索 |
| **命令注入** | Web 界面拼接系统命令 | 高 | 静态分析 + 动态验证 |
| **栈溢出** | 协议解析越界写 | 高 | Fuzzing + 逆向 |
| **认证绕过** | 逻辑缺陷（如只查前几位） | 高 | 代码审计 |
| **信息泄露** | 调试接口未关闭 | 中 | 端口扫描 + 串口 |
| **弱加密** | 自定义算法 / 固定密钥 | 中 | 逆向加密函数 |

### 四、完整的漏洞挖掘流程

```
① 信息收集
    · 设备型号、固件版本（从 Web/SNMP/标签）
    · 官网找固件升级包
        ↓
② 固件提取
    · binwalk -e
    · 找到文件系统、关键二进制
        ↓
③ 静态分析
    · 搜硬编码字符串（密码、密钥、URL）
    · 找危险函数（strcpy / system / sprintf）
    · 定位协议解析函数
        ↓
④ 动态分析
    · FirmAE / QEMU 仿真起来
    · gdb-multiarch 调试
    · 或者真机 + 串口调试
        ↓
⑤ 漏洞验证
    · 构造 PoC，确认可复现
    · 评估影响范围
        ↓
⑥ 负责任披露
    · 联系厂商（通常给 90 天）
    · 申请 CVE
    · 厂商修复后公开
```

### 五、静态分析的具体关注点

| 关注点 | 具体内容 |
|---|---|
| **危险函数** | `strcpy`、`strcat`、`sprintf`、`gets`、`memcpy`（无长度检查） |
| **命令执行** | `system`、`popen`、`exec*` |
| **硬编码字符串** | `password`、`admin`、`key`、`http://` |
| **加密相关** | `AES_`、`DES_`、自定义 S 盒 |
| **调试开关** | `debug`、`telnetd`、`gdb` |

**注意**：**"用了危险函数" ≠ "有漏洞"** —— 必须确认**输入是否可控**。
这是提高准确率、减少误报的关键。

### 六、动态分析方法

| 方法 | 工具 | 适用 |
|---|---|---|
| **固件仿真** | FirmAE、QEMU | 无真机时 |
| **调试** | gdb-multiarch | 有真机/仿真 |
| **流量分析** | tcpdump + Wireshark | 观察协议交互 |
| **模糊测试** | AFL++、BooFuzz | 找崩溃类漏洞 |
| **硬件调试** | OpenOCD + JTAG | 深层调试 |

### 七、负责任披露流程（必须遵守）

```
① 确认漏洞可复现
        ↓
② 私下联系厂商安全团队（不要公开）
        ↓
③ 给厂商修复时间（业界惯例 90 天）
        ↓
④ 申请 CVE 编号
        ↓
⑤ 厂商修复后，公开技术细节
```

> ⚠️ **法律与伦理红线**：
> - **只测试自有设备或明确授权的目标**
> - 遵守《网络安全法》《数据安全法》
> - **不公开未修复漏洞的利用细节**
> - 不做未授权的生产系统测试（**可能构成犯罪**）

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **程序逆向方向的直接应用** | 电力设备漏洞研究**影响力高** |
| **成果可见** | 可发表论文 + 可申请 CVE（有实际产出） |
| **适合做第一篇实证论文** | 周期可控（1 个设备 + 1 个洞） |
| **对接实验室方向** | **程序逆向**（核心）+ **工业AI**（自动化分析） |

> 💡 **一条务实的路线**：
> 「**某类电力设备固件的安全评估：从自动化扫描到漏洞验证**」

## Day 80 · 09:00 —— PLC 逻辑注入与梯形图攻击

> **一句话**：**PLC 是工业控制的执行大脑**——篡改它的**程序逻辑**（而不是数据）是最"物理"的攻击。

### 一、PLC 基础

| 维度 | 说明 |
|---|---|
| **全称** | 可编程逻辑控制器（Programmable Logic Controller） |
| **执行周期** | 输入采样 → 程序执行 → 输出刷新（循环扫描） |
| **扫描周期** | 通常 1 ~ 50 ms |
| **实时性** | **确定性**（这是它区别于普通计算机的核心） |

### 二、五种编程语言（IEC 61131-3）

| 语言 | 缩写 | 形式 | 使用率 |
|---|---|---|---|
| **梯形图** | LD | 图形（像继电器电路） | ⭐⭐⭐ 最高 |
| 功能块图 | FBD | 图形（逻辑门） | ⭐⭐ |
| 结构化文本 | ST | 类 Pascal 文本 | ⭐⭐ |
| 指令表 | IL | 汇编风格 | ⭐ |
| 顺序功能图 | SFC | 状态机 | ⭐ |

### 三、梯形图基础（看懂这几行就够）

```
    X0          X1                    Y0
 ───┤ ├─────────┤/├───────────────────( )───
   常开触点     常闭触点               线圈

含义：X0 接通 且 X1 断开 时，Y0 得电
```

| 符号 | 名称 | 含义 |
|---|---|---|
| `─┤ ├─` | 常开触点 | 条件成立时导通 |
| `─┤/├─` | 常闭触点 | 条件**不**成立时导通 |
| `─( )─` | 线圈 | 输出 |
| `─[ ]─` | 功能块 | 定时器、计数器等 |

### 四、PLC 的三种工作模式

| 模式 | 状态 | 用途 |
|---|---|---|
| **RUN** | 执行程序 | 正常运行 |
| **STOP** | **输出冻结** | 停机维护 |
| **PROGRAM** | 可下载程序 | 编程调试 |

> ⚠️ **STOP 模式很危险**：输出**保持最后状态**（不归零）。
> 如果攻击者在设备运行中切到 STOP，可能造成**设备卡在危险状态**。

### 五、五种攻击手法

| 攻击 | 手段 | 后果 | 难度 |
|---|---|---|---|
| **逻辑篡改** | 下载恶意程序 | 设备误动作 | 中（需编程权限） |
| **强制输出（Force）** | 直接写 I/O 点 | **绕过逻辑** | 低 |
| **切换 STOP** | 停止程序 | 生产中断 | 低 |
| **上传程序** | 读走程序 | **泄露工艺** | 低 |
| **固件篡改** | 刷恶意固件 | **持久化后门** | 高 |

### 六、典型攻击链

```
① 利用编程协议无认证（如 S7Comm、Modbus 编程功能）
        ↓
② 读取现有程序（了解工艺逻辑）
        ↓
③ 修改梯形图（如增加"在特定条件下误动作"的分支）
        ↓
④ 下载到 PLC
        ↓
⑤ PLC 按恶意逻辑运行，而 HMI 显示仍正常（Stuxnet 手法）
```

### 七、Stuxnet 的核心启示

Stuxnet 最精妙的地方**不是**篡改逻辑，而是：

```
① 篡改 PLC 逻辑 → 让离心机超速损坏
        ↓
② 同时篡改"回传给监控系统的数据" → 操作员看到一切正常
        ↓
③ 攻击持续数月未被发现
```

> 💡 **这是"数据与行为分离"攻击的典范** ——
> **行为已经恶意，但数据看起来正常**。这正是你在 Day 63 学的
> "$Ma = 0$ 让残差不变"的**物理世界版本**。

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **最"物理"的攻击** | 直接改变物理过程，后果立竿见影 |
| **检测难点** | 程序**语法合法**，只是逻辑恶意 → 静态扫描查不出 |
| **与 FDIA 同构** | 都是"让监控看到假的正常" |
| **对接实验室方向** | **入侵检测**（PLC 行为）+ **程序逆向**（梯形图分析） |

> 💡 **一个很好的选题**：
> 「**PLC 梯形图逻辑的语义异常检测：从"语法合法"到"行为合理"**」
> - 传统方法：检查程序**有没有语法错误**（没用，攻击者的程序语法完全正确）
> - 你的方法：建立"**正常控制逻辑的行为模型**"，检测逻辑的**语义偏离**
>   - 例如：正常程序不会在"无故障信号"时输出跳闸
>   - 例如：正常程序的输出应该能由输入**推导出来**（因果一致性）
> - 优势：**问题新颖**（PLC 逻辑安全研究少）、**可仿真**（用 OpenPLC 等开源软 PLC）

### 🔍 延伸思考

1. 如何检测"**逻辑被篡改但语法合法**"？需要什么信息（程序基线？行为模型？）
2. **Force 操作**（强制 I/O）如何被监控？它一定是恶意的吗？

- IEC 61131-3（PLC 编程语言标准）
- Langner, *To Kill a Centrifuge*（Stuxnet 技术分析报告）⭐

## Day 80 · 14:00 —— 硬件安全与侧信道

> **一句话**：**当软件防护到位时，攻击者会转向硬件**——侧信道、故障注入、硬件木马。

### 一、硬件攻击的三大类

| 类型 | 是否需要开盖 | 典型手段 | 成本 |
|---|---|---|---|
| **侵入式** | ✅ 是 | 开盖、微探针、FIB | 极高 |
| **半侵入式** | ⚠️ 部分 | 激光、紫外光、背面攻击 | 高 |
| **非侵入式** | ❌ 否 | **侧信道、故障注入** | **低~中** |

> 💡 **非侵入式最危险** —— 因为**不需要物理接触设备内部**，
> 甚至可以在设备正常运行时进行。

### 二、侧信道攻击的五种类型

| 类型 | 观测什么 | 说明 | 电力场景 |
|---|---|---|---|
| **功耗分析** | 电流波形 | SPA / **DPA** | 加密芯片密钥提取 |
| **电磁分析** | 电磁辐射 | EMA（可远距离） | 保护装置定值 |
| **时序分析** | 执行时间 | 简单但有效 | 密码比较函数 |
| **声音分析** | 声波 | 变压器嗡鸣、电容啸叫 | **推断负载** |
| **缓存分析** | Cache 命中 | 软件侧信道 | 云环境 |

**DPA（差分功耗分析）原理**：
```
正确密钥猜测 → 功耗模型与实际功耗相关性高
错误密钥猜测 → 相关性低
        ↓
遍历所有密钥猜测，相关性最高的就是正确密钥
```

### 三、故障注入

| 方法 | 原理 | 精度 |
|---|---|---|
| **电压毛刺** | 瞬时降压，跳过指令 | 中 |
| **时钟毛刺** | 打乱时序，跳过判断 | 中 |
| **激光** | 精确翻转某个位 | **高** |
| **温度** | 极端温度导致错误 | 低 |
| **电磁脉冲** | 远距离干扰 | 中 |

**经典应用**：**跳过"密码校验"的跳转指令** → 直接通过认证。

### 四、硬件木马

```
芯片设计阶段 → 植入恶意电路
    ↓
制造阶段 → 或修改版图
    ↓
封装后 → 完全无法通过软件检测
    ↓
触发条件满足时 → 泄露密钥 / 拒绝服务
```

**供应链风险**：电力设备大量使用第三方芯片 → **无法完全信任**。

### 五、电力系统中的侧信道问题

| 场景 | 问题 | 影响 |
|---|---|---|
| **智能电表** | 功耗曲线可推断**用户行为** | **隐私泄露** |
| **加密芯片** | 密钥可被 DPA 提取 | 认证失效 |
| **保护装置** | 定值、密钥可提取 | 安全机制被绕过 |
| **变压器** | 声音分析推断负载 | 生产信息泄露 |
| **NILM** | 非侵入式负荷监测 | **本身就是侧信道技术** |

> 💡 **NILM 的双面性**：
> 电力公司用 NILM（从总功耗推断各电器用电）做**需求侧管理** —— 这是**正当应用**。
> 但同样的技术可以推断"**家里有没有人**""**什么时候睡觉**""**用什么电器**" —— 这是**隐私侵犯**。
> **同一技术，两种用途** —— 这正是「AI 与数据安全」方向的核心议题。

### 六、防御手段

| 层面 | 措施 |
|---|---|
| **算法层** | 掩码（Masking）、隐藏（Hiding） |
| **电路层** | 双轨逻辑（Dual-rail）、随机化 |
| **物理层** | 屏蔽罩、滤波器 |
| **系统层** | 传感器监控（检测异常电压/温度） |
| **供应链** | 芯片来源审计、X 射线检测 |

### 七、研究机会

| 方向 | 说明 | 难度 |
|---|---|---|
| **电力设备侧信道** | 研究较少（相比智能卡） | 高 |
| **智能电表隐私保护** | 与「AI与数据安全」直接对接 | 中 |
| **NILM 的隐私-效用权衡** | 既要用数据又要保护隐私 | **中** |
| **硬件木马检测** | 极难 | 极高 |

### 🔗 与网安研究关联

| 要点 | 说明 |
|---|---|
| **硬件是"最后的攻击面"** | 软件防住了，就往下打 |
| **智能电表隐私 = AI 与数据安全** | 直接对接实验室方向 |
| **NILM 是"隐私 vs 效用"的经典案例** | 可以做差分隐私、联邦学习 |
| **对接实验室方向** | **隐私保护 / 可信计算**（核心）+ 入侵检测（物理异常） |

> 💡 **一个很适合你的选题**：
> 「**智能电表数据的隐私保护：基于差分隐私的 NILM 可用性保持**」
> - **问题**：电表数据既要用于负荷监测（效用），又不能泄露用户行为（隐私）
> - **方法**：差分隐私 + 时序建模，在保证 NILM 精度的前提下加入噪声
> - **优势**：
>   - **数据可得**（公开电表数据集如 REDD、UK-DALE）
>   - **指标清晰**（隐私预算 $\varepsilon$ vs NILM 精度）
>   - **直接对接「AI与数据安全」方向**
>   - 而且和你已有的 FDIA 方向**互补**（一个攻、一个防隐私）

2. 为什么电力设备对侧信道攻击**特别脆弱**？（提示：部署环境、生命周期）

## Day 81 · 09:00 —— 第十一周复盘：协议安全的共性规律

> **一句话**：**把本周所有协议的缺陷归纳起来，你会发现它们违反的是同几条根本原则**。

### 一、本周协议全景对比

| 协议 | 用途 | 协议层 | 原生安全机制 | 主要缺陷 | 高危操作 |
|---|---|---|---|---|---|
| **Modbus** | PLC 通信 | 应用层 | ❌ **无** | 完全无安全设计 | 写寄存器/线圈 |
| **DNP3** | 电力远动 | 应用层 | ⚠️ SAv5（可选） | 部署率低、可降级 | 遥控 |
| **IEC 104** | 调度远动 | 应用层 | ❌ **无** | 无认证 | **遥控（TI=45）** |
| **IEC 61850 MMS** | 变电站 | 应用层 | ⚠️ 62351 后补 | 可写保护定值 | **写定值** |
| **GOOSE / SV** | 站内实时 | **二层** | ⚠️ 62351-6 后补 | 可伪造跳闸 | **伪造跳闸** |
| **OPC UA** | 系统集成 | 应用层 | ✅ **原生完整** | **配置错误** | 写节点 |

### 二、共性缺陷归纳

| 缺陷 | 涉及协议 | 根本原因 |
|---|---|---|
| **无认证** | Modbus、104、61850 | 设计时代**没有威胁模型** |
| **无加密** | Modbus、104、61850、GOOSE | **性能优先**（加密有开销） |
| **无完整性校验** | 同上 | 依赖**物理隔离** |
| **可降级** | DNP3、OPC UA | **兼容性需求**（要支持老设备） |
| **配置风险** | OPC UA | **复杂度**（机制越多，配错机会越多） |

### 三、三条根本规律（本周最重要的收获）

```
规律 ①：协议安全的"时代错位"
    为"物理隔离环境"设计的协议
            ↓ 被搬到了
    "联网环境"
            ↓
    安全假设全部失效
    （Modbus 1979 年设计时，世界上还没有"网络攻击"这个词）

规律 ②：安全与实时的根本矛盾
    GOOSE 要求 4 ms 内送达
            vs
    数字签名验证需要时间
            ↓
    这个矛盾无法用纯软件解决 → 需要硬件加速或新方案

规律 ③：兼容性的代价
    为了支持存量老设备
            ↓
    必须保留"不安全的降级选项"
            ↓
    攻击者总能诱导降级
    （SSL Strip 与 DNP3 SA 降级是同一类攻击）
```

### 四、为什么这些缺陷"难修"

| 原因 | 说明 |
|---|---|
| **存量设备多** | 全国几百万台设备，换不起 |
| **标准已冻结** | 改了就不兼容，产业链不接受 |
| **实时性约束** | 加安全开销可能违反实时要求 |
| **生命周期长** | 电力设备寿命 20~30 年 |
| **责任分散** | 厂商、集成商、运维方各管一段 |

> 💡 **这五条解释了为什么工控安全"知道问题却解决不了"** ——
> **技术问题背后是工程和经济问题**。理解这一点，你的论文才不会"纸上谈兵"。

### 四、实现五步

```
① tshark 导出字段 → CSV
② pandas 读入
③ 特征提取（五维度）
④ 异常规则匹配
⑤ 输出报告
```

### 五、代码骨架（Modbus 版）

```python
# ---------- ① 用 tshark 导出字段 ----------
# tshark -r traffic.pcap -Y modbus -T fields \
#   -e frame.time_epoch -e ip.src -e ip.dst \
#   -e modbus.func_code -e modbus.reference_num -e modbus.word_cnt \
#   -E header=y -E separator=, > modbus.csv

import pandas as pd
import numpy as np

df = pd.read_csv("modbus.csv")
df.columns = ["time", "src", "dst", "func", "addr", "cnt"]

# ---------- ② 特征提取 ----------
feats = {}

# 维度1：通信关系（有几对 src-dst）
feats["n_pairs"] = df.groupby(["src", "dst"]).ngroups

# 维度2：操作类型（读 vs 写）
READ_CODES = {1, 2, 3, 4}
WRITE_CODES = {5, 6, 15, 16}
feats["write_ratio"] = df["func"].isin(WRITE_CODES).mean()

# 维度3：通信频率（时间间隔统计）
df = df.sort_values("time")
dt = df["time"].diff().dropna()
feats["dt_mean"] = dt.mean()
feats["dt_std"] = dt.std()
feats["dt_min"] = dt.min()

# 维度4：数值特征（地址范围）
feats["addr_min"] = df["addr"].min()
feats["addr_max"] = df["addr"].max()

# ---------- ③ 异常规则 ----------
alerts = []

if feats["write_ratio"] > 0.1:
    alerts.append(f"⚠️ 写操作占比 {feats['write_ratio']:.1%}（正常应 < 1%）")

if feats["dt_min"] < 0.001:      # 间隔 < 1ms
    alerts.append(f"⚠️ 存在高频请求（最小间隔 {feats['dt_min']*1000:.2f} ms）")

# 出现未定义功能码
valid = READ_CODES | WRITE_CODES
bad = df[~df["func"].isin(valid)]
if len(bad) > 0:
    alerts.append(f"⚠️ 出现 {len(bad)} 条未定义功能码")

# ---------- ④ 输出报告 ----------
print("=" * 50)
print("Modbus 流量分析报告")
print("=" * 50)
for k, v in feats.items():
    print(f"  {k:15s} = {v}")
print("-" * 50)
if alerts:
    for a in alerts:
        print(" ", a)
else:
    print("  ✅ 未发现明显异常")
```

|---|---|---|
| **通信关系** | `src-dst` 对数 | 主站-从站对 |
| **操作类型** | 功能码分布 | **TI 分布（TI=45 高危）** |
| **通信频率** | 请求间隔统计 | 总召唤频率 |
| **数值特征** | 寄存器地址/值范围 | IOA 范围、遥测值 |
| **时间特征** | 请求时段分布 | 请求时段分布 |
